## 第1部：ストーリーで読む「AIエージェントを外部ツールと安全につなぐ」

IDEでのコーディングに慣れてきたミサキとPMのユイ。「せっかくならIssue確認、Figmaデザイン参照、DB調査、エラー追跡までAIに連携させたい」と相談を持ちかける。サトウが、標準プロトコルであるMCPの仕組みから実践連携、セキュリティ統制までを解説する。

---

### シーン1：MCPのアーキテクチャと3つの基本機能

**ユイ**：「開発スピードを上げるために、エージェントからGitHubやFigma、データベースを直接参照できるようにしたいんです。でも、ツールごとに個別実装すると保守が大変そうですよね？」

**サトウ**：「そこで登場するのが、AIアプリと外部ツール・データソースを標準形式で接続する**Model Context Protocol（MCP）**だよ。構成はシンプルで、外部機能を提供する**MCPサーバー**、接続とツール呼び出しを仲介する**MCPクライアント**、そして複数のクライアントや承認フローを統括するIDE側の**MCPホスト**の3役で成り立っている」

**ミサキ**：「MCPサーバーは何をAIに公開するんですか？」

**サトウ**：「主に3つ。検索やAPI実行などのアクションを提供する**MCP Tools**、ドキュメントやスキーマをURI形式で読ませる**MCP Resources**、そして定型テンプレートを呼べる**MCP Prompts**だ。通信規約には**JSON-RPC 2.0**が使われていて、ローカル実行なら標準入出力の**stdioトランスポート**、リモート接続なら**Streamable HTTPトランスポート**を選ぶのが定番だね」

**ミサキ**：「社内専用のMCPサーバーを自作したいときは大変ですか？」

**サトウ**：「PythonやTypeScriptなら**FastMCP**を使えばデコレータ数行で書けるし、動作確認もブラウザから対話デバッグできる**MCP Inspector**があるからすぐ作れるよ」

---

### シーン2：ツール呼び出しの仕組みとコンテキスト肥大化への対策

**ミサキ**：「裏側ではLLMがどうやってツールを呼んでいるんですか？」

**サトウ**：「基本は**Function Calling（Tool Use）**だ。LLMが自然言語の代わりに、**JSON Schema制約**に従った構造化JSON引数で関数呼び出しを要求する。さらに**Structured Outputs（構造化出力）**を使えばパース失敗を防げるし、独立した調査を1ターンで同時発行する**並列ツール呼び出し（Parallel Tool Calling）**で待ち時間も減らせるんだ」

**ユイ**：「じゃあ、社内の全SaaSのMCPサーバーを片っ端から全部つないでおけば便利ですね！」

**サトウ**：「実はそれが落とし穴なんだ。大量のツールを常時つなぐと、ツール説明文だけでトークン枠が圧迫されて精度が落ちる**ツール定義コンテキスト肥大化**が起きる。だから、起動時は全スキーマを読み込まず必要時に取得する**遅延ツールロード（Lazy Tool Loading）**や、数百のツールから関連候補だけを抽出する**動的ツール検索（Tool Search）**を組み合わせるのが鉄則だよ」

**ミサキ**：「なるほど！別のフレームワークで作られた専門エージェント同士が連携したいときはどうするんですか？」

**サトウ**：「ツール接続がMCPなら、エージェント間のタスク委譲や能力発見には**Agent2Agent（A2A）プロトコル**が標準になりつつある。役割を分けて組み合わせるのが今どきの設計だね」

---

### シーン3：開発現場で効くMCPサーバー群とオーケストレーション

**ミサキ**：「実際に私たちのプロジェクトでは、どんなMCPサーバーから導入するのがおすすめですか？」

**サトウ**：「まずは開発サイクルに直結する定番から入れよう。IssueやPRを扱う**GitHub MCPサーバー**、デザイン構造やトークンを読み取る**Figma MCPサーバー**、実ブラウザでE2E動作確認する**Playwright MCP**、スキーマ調査に強い**PostgreSQL MCPサーバー**、障害スタックトレースを取る**Sentry MCPサーバー**あたりは効果が大きい。さらにライブラリの最新公式ドキュメントをバージョン指定で引ける**Context7**を入れると、知識カットオフによる古いコード生成が激減するよ」

**ユイ**：「Sentryでエラーが出たら自動でエージェントが原因調査を始める、みたいな自動化もできますか？」

**サトウ**：「できるよ。外部イベントを受け取る**Webhookトリガー**で起動して、状態管理とループ制御に強い**LangGraph**や、TypeScriptでUI統合しやすい**Vercel AI SDK**でワークフローを組むんだ。複数プロバイダの呼び出しは**AIゲートウェイ（LiteLLM / Portkey）**で集約し、実行トレースやツール呼び出し履歴は**Langfuse**で可視化しておけば、本番運用でも迷子にならないよ」

### シーン4：MCP時代のセキュリティと安全な外部連携

**ユイ**：「すごく便利そうですが、外部のMCPサーバーをつないだり本番データに触れたりするのはセキュリティ面が心配です……」

**サトウ**：「ユイの懸念はすごく重要だ。まず認証はリモートMCP標準の**OAuth 2.1（MCP認証）**を使い、複数サーバーへの接続や監査ログを**MCP Gateway**で一元統制する。トークン権限は読み取り専用や特定リポジトリ限定にする**最小権限の原則（ツール接続）**を徹底しよう」

**ミサキ**：「MCP特有の攻撃手法ってあるんですか？」

**サトウ**：「悪意あるサーバーがツール説明文に隠し命令を仕込む**Tool Poisoning（ツールポイズニング）**や、承認後に定義をこっそり改ざんする**Rug Pull攻撃（MCP）**が知られている。さらに外部WebやIssue本文に紛れた悪意ある指示をデータとして分離する**プロンプトインジェクション対策（外部データ）**も不可欠だ」

**ユイ**：「データ削除や外部送信みたいな危険操作は防げますか？」

**サトウ**：「破壊的アクションの直前は必ず人間が確認する**Human-in-the-Loop（HITL）承認**を挟むこと。加えて、再試行しても重複更新が起きない**ツール実行の冪等性**、API上限を守る**レート制限・バックオフ制御**、巨大レスポンスでコンテキストを溢れさせない**ツール出力の切り詰め（Truncation）**まで設計して、初めて安心して任せられる連携基盤になるんだよ」

## 第2部：DUO式・高密度復習フレーズ（声に出して覚える5本）

1. **【MCPの基本構造と開発】**
   「**Model Context Protocol（MCP）** では、**MCPホスト** 内の **MCPクライアント** が **JSON-RPC 2.0** 経由で **MCPサーバー** の **MCP Tools**・**MCP Resources**・**MCP Prompts** を呼び出し、自作時は **FastMCP** と **MCP Inspector** で素早く検証する。」
2. **【構造化呼び出しとコンテキスト最適化】**
   「**Function Calling（Tool Use）** と **JSON Schema制約**・**並列ツール呼び出し（Parallel Tool Calling）** で高速に外部操作しつつ、**ツール定義コンテキスト肥大化** を防ぐため **遅延ツールロード（Lazy Tool Loading）** と **動的ツール検索（Tool Search）** を導入する。」
3. **【現場の定番MCPと最新ドキュメント】**
   「**GitHub MCPサーバー**・**Figma MCPサーバー**・**Playwright MCP**・**PostgreSQL MCPサーバー**・**Sentry MCPサーバー** に加え、**Context7** で最新公式ドキュメントを参照させることで開発精度を底上げする。」
4. **【自動化・観測・ゲートウェイ統合】**
   「**Webhookトリガー** から **LangGraph** や **Vercel AI SDK** のエージェントを起動し、**AIゲートウェイ（LiteLLM / Portkey）** と **Langfuse** でトラフィック統制と実行トレースを一元化する。」
5. **【MCPセキュリティと堅牢なAPI運用】**
   「**OAuth 2.1（MCP認証）** と **MCP Gateway**、**最小権限の原則（ツール接続）**、**Human-in-the-Loop（HITL）承認** を軸に、**Tool Poisoning（ツールポイズニング）** や **Rug Pull攻撃（MCP）**、**プロンプトインジェクション対策（外部データ）** に備える。」

## 第4部：現場で活かす深掘り解説

### 1. 実務の判断基準：MCPの3機能と接続方式の使い分け早見表

| 区分 | 代表例・方式 | 得意な場面 | 苦手な場面・注意点 |
|---|---|---|---|
| **MCP Tools** | 検索・Issue作成・SQL実行などのアクション | 副作用や動的クエリを伴う操作、外部API連携 | 権限を広げすぎると誤操作リスクが高い（破壊的操作はHITL必須） |
| **MCP Resources** | DBスキーマ・設定・ドキュメントのURI参照 | 読み取り専用の文脈提供、ファイルや状態のスナップショット取得 | 更新処理や複雑な検索パラメータの引き渡し |
| **MCP Prompts** | レビュー・障害調査などの定型テンプレート | チーム標準の問いかけ方や出力形式の再利用 | 動的な分岐が多い自律ワークフロー全体の制御 |
| **stdio / Streamable HTTP** | ローカル実行（stdio） vs リモート接続（HTTP） | stdioは個人端末の軽量連携、Streamable HTTPは社内共有・OAuth 2.1認証 | リモート公開時は認証・MCP Gateway・監査ログの設計が不可欠 |

> **現場の鉄則**：外部連携はまず「**読み取り専用のMCPサーバー**（GitHub / Sentry / Context7 / 参照用DB）」から始め、書き込み・削除系は **最小権限の原則** と **Human-in-the-Loop（HITL）承認** を組み込んだうえで段階的に解放するのが安全です。

---

### 2. よくある失敗パターン（アンチパターン）と回避策

#### 失敗①：便利なMCPサーバーを大量に常時接続して精度が落ちる
- **起きること**: ツール定義のスキーマだけで数万トークンを消費する **ツール定義コンテキスト肥大化** が発生し、LLMが誤ったツールを選んだりコストが跳ね上がったりする。
- **回避策**: プロジェクトごとに使うMCPサーバーを厳選し、多数のツールを扱う場合は **遅延ツールロード（Lazy Tool Loading）** や **動的ツール検索（Tool Search）** で必要なツール定義だけを動的に読み込む。

#### 失敗②：本番権限のトークンをそのままMCPサーバーへ渡してしまう
- **起きること**: AIの誤解釈や外部データ経由の **プロンプトインジェクション** によって、意図しないデータ更新・削除や情報持ち出しが起きる。
- **回避策**: 認証は **OAuth 2.1（MCP認証）** やスコープ限定トークンで **最小権限の原則** を徹底し、破壊的操作には **Human-in-the-Loop（HITL）承認** を必須にする。社外製サーバーは **Tool Poisoning** や **Rug Pull攻撃** に備えて提供元とバージョンを固定検証する。

#### 失敗③：巨大レスポンスやAPIエラーでエージェントが無限ループする
- **起きること**: DBクエリやログ取得で巨大なJSONが返ってコンテキストが溢れたり、レート制限エラーに対して無制限リトライを繰り返したりして処理が破綻する。
- **回避策**: サーバー側で **ツール出力の切り詰め（Truncation）** とページネーションを実装し、**レート制限・バックオフ制御** と **ツール実行の冪等性** を組み込んだうえで、**Langfuse** などで実行トレースを監視する。

### 3. 明日から試せる実践レシピ（3ステップ）

1. **まずは読み取り専用MCPを1つだけ導入する**: 普段使っているIDEやCLIに、**Context7**（最新ドキュメント参照）または読み取り権限のみの **GitHub MCPサーバー** を接続し、手作業のコピペが減る効果を体感する。
2. **社内向けミニMCPをFastMCPで試作する**: よく使う社内APIやログ検索を **FastMCP** で1〜2ツールだけ実装し、**MCP Inspector** を使って引数スキーマ（**JSON Schema制約**）と出力サイズ（切り詰め）をブラウザ上で検証する。
3. **承認フローと権限境界を明文化する**: チームで接続するMCPサーバー一覧を棚卸しし、「自動許可（参照系）」「HITL承認必須（更新系）」「接続禁止（本番破壊系）」の3分類を決めて運用する。

### 4. 理解度チェック・ミニクイズ

**Q1. 多数のMCPサーバーを常時接続した結果、ツール説明文だけでコンテキスト枠が圧迫され、推論精度が落ちてしまいました。この現象の名称と代表的な対策は何ですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：ツール定義コンテキスト肥大化（対策：遅延ツールロード / 動的ツール検索）**
起動時に全ツールのJSON Schemaを読み込まず、必要なときに取得する **遅延ツールロード（Lazy Tool Loading）** や、タスクに関連する候補だけを絞り込む **動的ツール検索（Tool Search）** を使うことで精度とコストを改善できます。

</details>

**Q2. 信頼していた外部MCPサーバーが、初回承認後にツール説明文をこっそり書き換えて悪意ある命令を仕込む攻撃手法を何と呼びますか？**
<details>
<summary>解答と解説を見る</summary>

**答え：Rug Pull攻撃（MCP）**
ツール説明文に隠し命令を埋め込む **Tool Poisoning（ツールポイズニング）** と組み合わせ、承認後に定義をすり替える手口です。信頼できる配布元の利用、バージョン固定、**MCP Gateway** による一元統制が有効です。

</details>

**Q3. MCPで外部ツールを呼び出す機能とは別に、異なるフレームワークで構築された専門エージェント同士がタスクを委譲・連携するための標準プロトコルは何ですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：Agent2Agent（A2A）プロトコル**
MCPが「エージェントとツール・データソースの接続」を担うのに対し、**Agent2Agent（A2A）プロトコル** は「エージェント同士の能力発見とタスク委譲」を標準化します。両者を役割分担させて組み合わせるのが現代的な設計です。

</details>
