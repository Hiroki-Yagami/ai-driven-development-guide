## 第1部：ストーリーで読む「チーム標準のルール・スキルと安全な隔離実行環境」

いよいよチーム全体でAI駆動開発を本格運用するフェーズに入った。ミサキは「メンバーごとにAIの書き方がバラバラになる」、ユイは「AIが危険なコマンドや機密漏洩を起こさない仕組みが必要」と課題を挙げる。サトウが、ルール・スキル設計からサンドボックス隔離、検証ハーネス、組織ガバナンスまでをまとめ上げる。

---

### シーン1：ルールファイル・カスタムスキル・フックによる標準化

**ミサキ**：「AIに毎回『このプロジェクトのテストコマンドと規約はこうで……』って説明するのが大変です。チーム共通の指示を自動化できませんか？」

**サトウ**：「そこで使うのがプロジェクト指示ファイルだよ。複数ツール横断で標準化が進む**AGENTS.md**、Claude Code向けの**CLAUDE.md**、Cursorで条件適用できる**.cursorrules / .cursor/rules（MDC）**などをリポジトリに置くんだ。グローバル→ルート→サブディレクトリと上書きする**階層的ルール継承（Hierarchical Rules）**や、テストファイル編集時だけ規約を差し込む**パス条件付きルール適用（Glob Scoping）**を使うと、トークンを無駄にせず精度を保てるよ」

**ミサキ**：「複雑なデプロイ手順や障害調査フローもまとめられますか？」

**サトウ**：「定型の手順書や補助スクリプトは**カスタムスキル（Agent Skills / SKILL.md）**としてフォルダ単位でパッケージ化しよう。普段は短い説明だけ読ませ、該当タスクのときだけ詳細を開く**段階的開示（Progressive Disclosure）**が効くんだ。対話で確立したノウハウを資産化する**ワークフローのスキル化（Workflow Distillation）**を進め、関連スキルやMCPをまとめた**プラグインバンドル（Agent Plugins）**で配布すればチーム全体が一気に底上げされるよ」

**ミサキ**：「編集後の自動フォーマットや危険コマンド防止も自動化できますか？」

**サトウ**：「それが**エージェントフック（Lifecycle Hooks）**だ。実行前に危険操作を止める**PreToolUseガードフック**と、編集直後にFormatterを走らせる**PostToolUse自動整形フック**を組み合わせれば、AIが常に規約準拠のコードを出してくれるようになるよ」

### シーン2：サンドボックス隔離と最小権限の安全設計

**ユイ**：「エージェントにシェルコマンドを実行させるとき、ホストPCのファイルや本番環境を壊すリスクが気になります」

**サトウ**：「だから**サンドボックス実行環境（Agent Sandbox）**で隔離するのが大前提だ。ローカル軽量隔離なら**OSネイティブサンドボックス（Seatbelt / Bubblewrap）**、開発環境丸ごとの再現と隔離なら**Dev Containers（devcontainer.json）**を使う。クラウド上で信頼できないコードを安全かつ高速に回すなら、カーネル分離できる**マイクロVM（Firecracker / Kata Containers）**や専用APIの**E2B（Code Interpreter Sandbox）**が強力だね」

**ミサキ**：「環境が汚れて前のタスクの影響が残ることはありませんか？」

**サトウ**：「タスクやPRごとに使い捨てて破棄する**エフェメラル環境（使い捨て実行環境）**を徹底すれば状態汚染を防げる。さらに、ワークスペースと `/tmp` 以外を遮断する**ファイルシステムアクセス境界**、外部通信をデフォルト禁止する**エグレス制御（ネットワーク遮断）**も組み合わせるんだ」

**ユイ**：「コマンドごとの承認ルールはどう設計すればいいでしょう？」

**サトウ**：「読み取りは自動許可、テスト実行は条件付き許可、破壊的操作は承認必須または禁止にする**権限承認ポリシー（Allow / Ask / Deny）**を定義しよう。`DROP TABLE` や `rm -rf` を止める**データ損失防止ガード（DLP / Safety Gate）**を入れ、全実行履歴を**監査ログ（Audit Trail）**へ残せば、セキュリティ監査にも耐えられるよ」

### シーン3：セキュリティ検査と高速フィードバックのハーネス設計

**ミサキ**：「AIが書いたコードに脆弱性やAPIキーが混ざるのを自動で防ぐ方法はありますか？」

**サトウ**：「品質と安全性を支える仕組みづくりを**ハーネスエンジニアリング（Harness Engineering）**と呼ぶんだ。まず秘密情報の混入を止める**シークレットスキャン（Gitleaks / TruffleHog）**、脆弱性を検出してAIへフィードバックする**静的解析・SAST統合（Semgrep / CodeQL）**、送信前に個人情報を伏せる**PIIマスキング・匿名化プロキシ**を導入しよう。あと、LLMが幻覚で出した架空パッケージ名を悪用される**Slopsquatting（スロップスクワッティング）**にも注意が必要だよ」

**ミサキ**：「エージェントの修正ループをもっと速く正確にするコツはありますか？」

**サトウ**：「ツールの実行速度がそのままエージェントの賢さに直結する。Python環境なら超高速な**uv（高速Python環境管理）**、静的検査と整形にはミリ秒で終わる**超高速Linter/Formatter（Biome / Ruff / Oxlint）**を選ぶ。結合テストは本番DBに触らず一時コンテナを立てる**Testcontainers**で回し、AI生成テストの形骸化を防ぐために意図的にバグを注入して検出力を測る**ミューテーションテスト（Stryker / mutmut）**も効くよ。そして完了報告前には必ずビルドとテストの一次証拠を確認させる**チェックリスト駆動検証（Verification Before Completion）**をルール化しよう」

### シーン4：安全なリリース基盤・組織ガバナンス・エコシステム統合

**ユイ**：「複数チームへ広げていくときのガバナンスやリリース安全性はどう整えればいいですか？」

**サトウ**：「まず、非承認ツールへのコード貼付を防ぐ**シャドーAI対策**として、安全で使いやすい公式環境と**チーム横断ルール配布（Shared Config Repo）**を整える。そして忘れてはいけないのが、AIが生成したコードでもマージした開発者・チームが保守責任を持つという**AI生成コードの所有権・説明責任**の原則だよ」

**ユイ**：「インフラ変更やDBマイグレーションを伴うPRの検証はどうしましょう？」

**サトウ**：「適用前に影響をシミュレーションする**ドライラン（Dry-Run）実行**、PRごとに動作確認環境を自動生成する**プレビュー環境自動生成（PR Preview）**、さらにコピーオンライトでDBを瞬時に複製できる**データベースブランチング（Neon / PlanetScale）**を使えば、本番無傷のまま実動作を検証できる。セキュリティ規則も**Policy as Code（Open Policy Agent / OPA）**で機械判定すれば属人化しないよ」

**ミサキ**：「IDE、MCP、推論モデル、RAG、そしてスキルとサンドボックスまで、全部がつながって1つの開発基盤になるんですね！」

**サトウ**：「そう。すべてを疎結合に組み合わせて継続進化させる全体像こそが**AI駆動開発エコシステム統合**なんだ。これでチーム全員が安全かつ爆速で価値を届けられるね！」

1. **【ルール・スキル・フックの自動化】**

## 第4部：現場で活かす深掘り解説

### 1. 実務の判断基準：ルール・スキル・フックと隔離環境の使い分け

| 仕組み | 代表例 | 得意な場面 | 苦手な場面・注意点 |
|---|---|---|---|
| **ルールファイル** | AGENTS.md / CLAUDE.md / .cursor/rules | プロジェクト全体の基本規約、技術スタック、禁止事項の常時共有 | 長大化するとコンテキストを圧迫し遵守率が落ちる（Glob Scopingで絞る） |
| **カスタムスキル（SKILL.md）** | 障害調査・デプロイ手順・専用スクリプト群 | 特定タスク時だけ呼び出す専門手順のパッケージ化（段階的開示） | 全作業に常に強制したい単純ガード（ルールやフック向き） |
| **ライフサイクルフック** | PreToolUse / PostToolUse | 危険コマンドの機械的ブロック、編集直後の自動Lint・整形 | 曖昧な設計判断や文脈依存のレビュー（プロンプト・スキル向き） |
| **隔離サンドボックス** | OSネイティブ / Dev Containers / マイクロVM / E2B | 自律コマンド実行、CI・クラウドでの未検証コード実行 | 隔離レベルが上がるほど起動コスト・設定難度も上がるため用途で選定 |

> **現場の鉄則**：「**必ず守らせたいことはプロンプトではなくフック・Linter・サンドボックスで機械的に強制し、判断が要る規約はルールとスキルで簡潔に伝える**」のが、信頼できる **ハーネスエンジニアリング** の基本です。

### 2. よくある失敗パターン（アンチパターン）と回避策

#### 失敗①：ルールファイルに全社規約を詰め込みすぎてAIが無視し始める
- **起きること**: `AGENTS.md` が数百行に膨れ上がり、タスクに無関係な規約でコンテキストが埋まって重要な指示まで見落とされる。
- **回避策**: ルールファイルは要点だけに絞り、詳細手順は **カスタムスキル（SKILL.md）** へ切り出して **段階的開示（Progressive Disclosure）** を使う。ファイル種別ごとの規約は **パス条件付きルール適用（Glob Scoping）** と **階層的ルール継承** で必要時だけ適用する。

#### 失敗②：ホスト環境のまま全自動許可で動かし、意図しない破壊や機密流出を招く
- **起きること**: エージェントの誤コマンドでホストPCの設定や別リポジトリを壊したり、外部へ機密ファイルやAPIキーを送信してしまったりする。
- **回避策**: **サンドボックス実行環境**（OSネイティブ隔離・**Dev Containers**・**マイクロVM** 等）で **ファイルシステムアクセス境界** と **エグレス制御** を敷く。さらに **権限承認ポリシー（Allow / Ask / Deny）** と **PreToolUseガードフック**、**シークレットスキャン（Gitleaks等）** で多層防御する。

#### 失敗③：AIの「修正しました・テスト通りました」をそのまま信用してマージする
- **起きること**: 実際にはテストが未実行だったり、アサーションが空の形骸化テストになっていたり、架空パッケージ名による **Slopsquatting** リスクが紛れ込んだりする。
- **回避策**: **チェックリスト駆動検証（Verification Before Completion）** でビルド・Lint・テストの実行ログを必須化し、**超高速Linter/Formatter（Ruff / Biome等）**、**SAST（Semgrep / CodeQL）**、**Testcontainers**、重要ロジックには **ミューテーションテスト** を組み込む。最終責任は人間が持つ **AI生成コードの所有権・説明責任** を徹底する。

### 3. 明日から試せる実践レシピ（3ステップ）

1. **最小の `AGENTS.md` を30行以内で置く**: リポジトリのビルド・テスト・Lintコマンド、ディレクトリ構造、やってはいけない禁止事項だけを短く記述し、チーム全員で同じ前提をAIへ渡せる状態を作る。
2. **「自動整形」と「危険コマンド防止」のフックを1つずつ入れる**: 編集後に **Biome / Ruff** などを走らせる **PostToolUse自動整形フック** と、`rm -rf` や本番DB操作を止める **PreToolUseガードフック** を導入し、品質と安全を自動化する。
3. **うまくいった作業手順を1つスキル化する**: AIとの対話で再現できた定型フロー（例：PRレビュー手順、マイグレーション確認）を `SKILL.md` へ整理し（**ワークフローのスキル化**）、次のタスクから再利用してみる。

### 4. 理解度チェック・ミニクイズ

**Q1. 普段は短い説明文だけをエージェントに見せ、該当タスクが発生したときだけ詳細な手順書やスクリプトを読み込ませることで、コンテキスト消費を抑える設計パターンは何ですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：段階的開示（Progressive Disclosure）**
**カスタムスキル（Agent Skills / SKILL.md）** の中核設計であり、大量の専門ノウハウをリポジトリに抱えていても、通常時のトークン圧迫と精度劣化を防げます。

</details>

**Q2. LLMがハルシネーションで存在しないパッケージ名を出力する傾向を悪用し、攻撃者がその架空名でマルウェア入りパッケージを公開しておくサプライチェーン攻撃を何と呼びますか？**
<details>
<summary>解答と解説を見る</summary>

**答え：Slopsquatting（スロップスクワッティング）**
AIが提案した新規依存ライブラリは鵜呑みにせず、実在性・メンテナ・ダウンロード数を確認し、ロックファイルと **静的解析・SAST** や依存監査をCIに組み込むことが重要です。

</details>

**Q3. エージェントが自律的にコードを修正する際、人間が手作業で都度注意するのではなく、Linter・テスト・サンドボックス・フックなどの検証基盤全体を整えて品質と安全性を引き上げるアプローチを何と呼びますか？**
<details>
<summary>解答と解説を見る</summary>

**答え：ハーネスエンジニアリング（Harness Engineering）**
モデル単体の性能に頼るのではなく、高速なフィードバックループとガードレール（検証ハーネス）を設計することで、AIエージェントの実用精度と安全性を飛躍的に高められます。

</details>
