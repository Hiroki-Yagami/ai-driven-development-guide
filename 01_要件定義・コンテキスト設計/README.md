# 01_要件定義・コンテキスト設計 キーワード辞典（500選）

AI駆動型開発において、AIエージェントが正確に意図を汲み取り、高品質な設計・実装を行うための「要件定義」および「コンテキスト設計」に関する500の重要キーワードを5つの領域に分類して解説する。

---

## 1. 要件定義・仕様駆動開発（1〜100）

1. **仕様駆動開発（SDD: Spec-Driven Development）**: 実装より先に厳密な仕様書を作成し、それを唯一の正としてAIにコード生成やテストを行わせる開発手法。
2. **要件定義書（PRD: Product Requirements Document）**: プロダクトの目的、対象ユーザー、機能要件、成功指標を体系的にまとめた最上位の仕様文書。
3. **機能要件（Functional Requirements）**: システムが提供すべき具体的な機能や振る舞い、入出力の仕様を定義した要件。
4. **非機能要件（Non-Functional Requirements）**: 性能、可用性、セキュリティ、拡張性、保守性など、機能以外の品質特性を規定する要件。
5. **受け入れ基準（Acceptance Criteria）**: ある機能やストーリーが完了したとみなすための客観的かつ検証可能な合格条件。
6. **Given-When-Then記法**: 前提条件・操作・期待結果を構造化して記述するBDD形式の受け入れ基準表現。
7. **ユーザーストーリー（User Story）**: 「誰が・何を・なぜ求めるか」を簡潔に記述し、AIと人間が開発価値を共有するための要件単位。
8. **エピック（Epic）**: 複数のユーザーストーリーを束ねる大きな機能群やビジネス目標の単位。
9. **ジョブ理論（JTBD: Jobs to be Done）**: ユーザーがプロダクトを「雇用」して達成したい本質的な目的から要件を導き出す思考枠組み。
10. **ユースケース（Use Case）**: アクターとシステムの相互作用を通じて特定の目的を達成する一連のシナリオ定義。
11. **ユースケースシナリオ（Use Case Scenario）**: 基本フロー・代替フロー・例外フローに分けて具体的な操作手順を記述した仕様。
12. **業務フロー（Business Process Flow）**: 業務全体の流れや担当者間の受け渡しを可視化し、システム化対象範囲を特定するための図表。
13. **要件トレーサビリティ（Requirements Traceability）**: ビジネス要求から仕様・設計・コード・テストまでを一貫して追跡可能にする管理手法。
14. **トレーサビリティマトリクス（RTM）**: 要件IDと設計書・テストケース・実装ファイルの対応関係を一覧化した検証用マトリクス。
15. **スコープ定義（Scope Definition）**: 今回の開発で「やること（In-Scope）」と「やらないこと（Out-of-Scope）」を明確に線引きする作業。
16. **アウトオブスコープ（Out of Scope）**: 意図的に対象外とする機能や条件を明示し、AIの過剰実装（オーバーエンジニアリング）を防ぐ制約。
17. **スコープクリープ（Scope Creep）**: 合意のないまま要件が際限なく膨張し、設計破綻や納期遅延を招く現象。
18. **MoSCoW法**: 要件をMust・Should・Could・Won'tの4段階に分類し、実装優先度を明確化する手法。
19. **MVP（Minimum Viable Product）**: 仮説検証に必要な最小限の機能のみを備えた初期プロダクトの要件範囲。
20. **MLP（Minimum Lovable Product）**: 最小機能でありながらユーザーが継続利用したくなる体験価値を備えた初期要件水準。
21. **Kanoモデル**: 当たり前品質・一元的品質・魅力的品質の分類により、機能投資の優先順位を判断するモデル。
22. **RICEスコアリング**: Reach・Impact・Confidence・Effortの4軸で要件や施策の優先度を定量評価する手法。
23. **価値仮説（Value Hypothesis）**: 提案する機能がユーザーに真の価値をもたらすかどうかを検証するための前提命題。
24. **成長仮説（Growth Hypothesis）**: ユーザー獲得や継続利用がどのように拡大するかを定義したビジネス要件の前提。
25. **ペルソナ設計（Persona Design）**: ターゲットユーザーの属性・課題・行動特性を具体化し、UIや機能判断の軸とする手法。
26. **カスタマージャーニーマップ**: ユーザーの認知から利用・離脱までの体験と感情変化を時系列で可視化した設計資料。
27. **サービスブループリント**: ユーザー体験の表層だけでなく、裏側の業務プロセスやシステム連携まで俯瞰する設計図。
28. **問題定義書（Problem Statement）**: 解決すべき課題の本質・影響範囲・現状の痛みを端的に明文化したドキュメント。
29. **ビジネス要件定義書（BRD）**: 経営課題や事業目標の達成に向けてシステムが満たすべきビジネス上の要求を記した文書。
30. **ソフトウェア要件仕様書（SRS）**: システムの外部インターフェース、データ構造、制約条件を詳細に規定する技術仕様書。
31. **EARS記法（Easy Approach to Requirements Syntax）**: 曖昧さを排除するために「When / While / If〜then」の定型構文で要件を記述する手法。
32. **SMART原則**: 要件や目標を具体的・測定可能・達成可能・関連性あり・期限明確の5基準で精査する指針。
33. **INVEST原則**: 良質なユーザーストーリーの条件（独立・交渉可能・価値・見積可能・小規模・検証可能）を示す指標。
34. **曖昧さ排除（Disambiguation）**: 「高速に」「使いやすく」といった主観的表現を数値や条件に置き換え、AIの誤解釈を防ぐ工程。
35. **エッジケース（Edge Case）**: 極端な入力値や稀な操作順序など、通常フローから外れる境界的な振る舞い条件。
36. **コーナーケース（Corner Case）**: 複数の異常条件や境界条件が同時に重なった際に発生する複合的な例外シナリオ。
37. **異常系要件（Exception Handling Requirements）**: ネットワーク障害、権限不足、不正入力などのエラー発生時にシステムが取るべき振る舞いの定義。
38. **境界値条件（Boundary Condition）**: 文字数上限・最小値・ゼロ・NULLなど、仕様の境界線上で厳密に定義すべき動作ルール。
39. **制約条件（Constraints）**: 法規制、予算、既存システム互換性、利用技術など、設計の自由度を制限する絶対条件。
40. **前提条件（Assumptions）**: 要件定義時点で成立しているとみなす環境・データ・運用上の仮定事項。
41. **依存関係（Dependencies）**: 外部API、他チーム開発機能、データ基盤など、要件実現のために必要な外部要素。
42. **SLA（Service Level Agreement）**: 稼働率や応答時間など、サービス提供者が保証する品質水準の合意仕様。
43. **SLO（Service Level Objective）**: SLAを満たすために内部で設定する具体的な信頼性・性能の目標値。
44. **SLI（Service Level Indicator）**: レスポンスタイムやエラー率など、SLOの達成度を測定するための定量的指標。
45. **RPO（Recovery Point Objective）**: 障害発生時に許容できるデータ損失の最大時間幅を規定する復旧要件。
46. **RTO（Recovery Time Objective）**: 障害発生からサービス復旧までに許容される最大停止時間の目標要件。
47. **パフォーマンス要件（Performance Requirements）**: レイテンシ、スループット、同時接続数など、処理速度と負荷耐性に関する数値要件。
48. **スケーラビリティ要件（Scalability Requirements）**: ユーザー数やデータ量の増加に応じて水平・垂直拡張できることを求める設計要件。
49. **セキュリティ要件（Security Requirements）**: 認証・認可、暗号化、監査ログ、脆弱性対策など安全性を担保するための必須仕様。
50. **プライバシー要件（Privacy Requirements）**: 個人情報保護法やGDPR等に準拠し、データ最小化や同意管理を規定する要件。
51. **コンプライアンス要件（Compliance Requirements）**: 業界規制、社内規定、法的義務にシステムを適合させるための順守項目。
52. **アクセシビリティ要件（Accessibility Requirements）**: WCAG等の基準に基づき、障害の有無に関わらず利用できるUI・操作性の要件。
53. **国際化・多言語要件（i18n / l10n Requirements）**: 言語切替、タイムゾーン、通貨、文字コードなど地域差に対応するための仕様。
54. **保守性要件（Maintainability Requirements）**: 変更容易性、テスト容易性、モジュール分離度など長期運用を見据えた品質要件。
55. **可観測性要件（Observability Requirements）**: ログ・メトリクス・トレースの収集方針を定め、障害調査を容易にする運用要件。
56. **データ移行要件（Data Migration Requirements）**: 既存システムから新システムへのデータ変換・クレンジング・切替手順を規定する要件。
57. **運用要件（Operational Requirements）**: バックアップ、監視、パッチ適用、サポート体制などリリース後の維持管理に関する要件。
58. **互換性要件（Compatibility Requirements）**: 対応ブラウザ、OSバージョン、既存APIとの後方互換性を明示する仕様。
59. **仕様ファースト（Spec-First）**: APIやデータスキーマの仕様ファイルを最初に確定し、実装とテストを自動生成する開発原則。
60. **契約ファースト開発（Contract-First Development）**: OpenAPIやGraphQLスキーマなどのインターフェース契約を起点にフロント・バックを並行開発する手法。
61. **実行可能仕様（Executable Specification）**: Gherkinやテストコードの形式で記述され、そのまま自動検証にかけられる仕様書。
62. **振る舞い駆動開発（BDD: Behavior-Driven Development）**: ユーザー視点の振る舞い仕様を自然言語に近い形式で定義し、実装とテストを駆動する手法。
63. **受け入れテスト駆動開発（ATDD）**: 開発着手前に受け入れテストを定義し、要件の誤解をなくしながら実装を進める手法。
64. **要件抽出（Requirements Elicitation）**: インタビュー、ワークショップ、ログ分析を通じてステークホルダーの潜在ニーズを引き出す活動。
65. **要件分析（Requirements Analysis）**: 抽出した要求の矛盾・重複・欠落を精査し、実現可能な仕様へと構造化する工程。
66. **要件妥当性確認（Requirements Validation）**: 定義した仕様が本当にユーザーやビジネスの本来の目的を満たしているか検証する活動。
67. **要件変更管理（Requirements Change Management）**: 仕様変更の影響範囲を評価し、承認・反映・履歴追跡を統制するプロセス。
68. **影響範囲分析（Impact Analysis）**: ある要件の変更が既存の機能・データ・外部連携に与える波及効果を特定する調査。
69. **ギャップ分析（Gap Analysis）**: 現状（As-Is）と理想状態（To-Be）の差分を洗い出し、開発すべき要件を明確化する手法。
70. **As-Is / To-Be分析**: 現行業務・システム構造と将来像を対比させ、変革ポイントと移行課題を特定するフレームワーク。
71. **フィージビリティスタディ（Feasibility Study）**: 技術的・経済的・運用的な観点から要件の実現可能性を事前検証する調査。
72. **スパイク（Spike）**: 不確実性の高い技術要件を解明するために、タイムボックスを切って行う検証用プロトタイプ作業。
73. **要件の粒度設計（Requirements Granularity）**: AIが1回のタスクで正確に処理できるよう、要件を適切なサイズに分割する設計技術。
74. **タスク分解（Task Decomposition）**: 大きな要件を独立して実装・検証可能なサブタスク群へと階層的に分解する工程。
75. **WBS（Work Breakdown Structure）**: 成果物ベースで必要な作業項目をツリー状に細分化し、抜け漏れを防ぐ構造化手法。
76. **縦切り分割（Vertical Slicing）**: UIからDBまで価値提供に必要な全層を薄く貫通する単位で要件を分割する設計手法。
77. **横切り分割（Horizontal Slicing）**: 画面層・API層・DB層といった技術レイヤー単位で要件やタスクを分割する手法。
78. **Definition of Ready（DoR）**: 要件やチケットがAIや開発者による実装に着手できる状態であることを保証する事前条件。
79. **Definition of Done（DoD）**: 実装・テスト・ドキュメント更新など、タスク完了時に必ず満たすべき統一品質基準。
80. **仕様の単一情報源（SSOT: Single Source of Truth）**: 要件や仕様の正本を1か所に集約し、AIと人間が常に同じ最新情報を参照できる状態。
81. **仕様ドリフト（Spec Drift）**: 実装の変更が仕様書に反映されず、ドキュメントとコードが乖離していく現象。
82. **リビングドキュメント（Living Documentation）**: コードやテストと連動して常に最新状態が維持される、生きた仕様書体系。
83. **仕様レビュー（Specification Review）**: 実装前に仕様書の論理矛盾・抜け漏れ・AIへの誤解誘発表現を点検する品質ゲート。
84. **形式手法（Formal Methods）**: 数学的記法や状態機械を用いて仕様の整合性や無矛盾性を厳密に検証するアプローチ。
85. **決定表（Decision Table）**: 複数の条件組み合わせとそれに対応する動作を網羅的に表形式で整理する仕様記述法。
86. **状態遷移表（State Transition Table）**: エンティティの全状態とイベントに対する遷移先・禁止遷移を漏れなく定義する表。
87. **状態遷移図（State Transition Diagram）**: ライフサイクル上の状態変化をノードとエッジで視覚化し、AIに状態ルールを伝える図。
88. **ビジネスルール（Business Rules）**: 割引計算、承認権限、有効期限など、ドメイン固有の判断基準や計算ロジックの明文化。
89. **データ辞書（Data Dictionary）**: システムで扱う全項目名・型・桁数・制約・業務的意味を統一管理するメタデータ定義。
90. **用語集（Glossary）**: プロジェクト固有の専門用語や略語を定義し、AIの用語混同を防ぐ基礎ドキュメント。
91. **要件ID体系（Requirement ID Scheme）**: `REQ-001` のように一意な識別子を付与し、仕様・コード・テスト間の参照を機械可読にする仕組み。
92. **成功指標（Success Metrics / KPI）**: リリース後に要件がビジネス目標を達成したかを判定するための定量的な測定基準。
93. **ノーススターメトリック（North Star Metric）**: プロダクトが顧客に届ける核心的価値を最もよく表す単一の最重要指標。
94. **ガードレールメトリクス（Guardrail Metrics）**: 主要KPIを追求する過程で悪化させてはならない安全性・品質・UXの防衛指標。
95. **リリース判定基準（Release Criteria）**: テスト通過率、重大バグ件数、性能基準など、本番公開を許可するための最終ゲート条件。
96. **ロールバック要件（Rollback Requirements）**: デプロイ後に重大障害が発生した際、安全に旧バージョンへ切り戻すための仕様と手順。
97. **フィーチャーフラグ要件（Feature Flag Requirements）**: 機能の段階公開や即時停止を制御するためのフラグ設計および廃止基準。
98. **A/Bテスト要件（Experimentation Requirements）**: 機能バリエーションの比較検証に必要な振り分け条件・ログ計測・統計評価の仕様。
99. **段階的ロールアウト（Gradual Rollout）**: 一部ユーザーから順次公開範囲を広げることでリスクを最小化するリリース要件設計。
100. **要件の自動検証（Automated Spec Validation）**: LinterやLLMチェッカーを用いて仕様書の曖昧さ・欠落・矛盾を機械的に検出する仕組み。

## 2. コンテキストエンジニアリング・情報設計（101〜200）

101. **コンテキストエンジニアリング（Context Engineering）**: AIエージェントが最適な判断を下せるよう、入力コンテキストの構成・粒度・取得順序を体系的に設計する技術。
102. **コンテキストウィンドウ（Context Window）**: LLMが1回の推論で同時に保持・参照できる最大トークン容量の枠。
103. **コンテキストバジェット（Context Budget）**: コンテキストウィンドウ内でシステム指示・仕様・コード・履歴に割り当てるトークン配分計画。
104. **コンテキスト汚染（Context Pollution）**: 無関係なログや古い議論が混入し、AIの推論精度や指示遵守率が低下する現象。
105. **コンテキスト劣化（Context Rot）**: 会話やコンテキストが長大化するにつれて、重要な制約や初期仕様への注意力が薄れる現象。
106. **Lost in the Middle現象**: 長いコンテキストの中央部分に配置された情報が、冒頭や末尾に比べてLLMに見落とされやすくなる特性。
107. **コンテキスト圧縮（Context Compression）**: 冗長な履歴や長大なドキュメントを要点を保ったまま要約・構造化し、トークン消費を削減する処理。
108. **コンテキストコンパクション（Context Compaction）**: 進行中のセッション履歴を重要な決定事項と現在状態のみに凝縮して引き継ぐ最適化手法。
109. **コンテキスト剪定（Context Pruning）**: 現在のタスクに不要となった過去のツール出力や無関係ファイルを明示的に除外する操作。
110. **コンテキスト分離（Context Isolation）**: 調査・設計・実装など役割ごとに別セッションやサブエージェントへ分け、情報の混濁を防ぐ設計。
111. **段階的開示（Progressive Disclosure）**: 全情報を最初から渡さず、必要に応じて概要から詳細へ段階的にコンテキストを読み込ませる設計原則。
112. **ジャストインタイム取得（Just-in-Time Retrieval）**: 事前に全資料を詰め込まず、タスク実行時に必要な情報だけを動的に検索・取得する戦略。
113. **コンテキストキャッシュ（Context Caching / Prompt Caching）**: 繰り返し参照するルールや仕様書をキャッシュし、推論コストとレイテンシを大幅に削減する仕組み。
114. **トークン効率（Token Efficiency）**: 少ないトークン数で最大限の情報密度と精度を引き出すコンテキスト記述の最適化指標。
115. **情報密度（Information Density）**: 冗長な修飾語を省き、仕様・制約・判断基準を凝縮して伝えるドキュメント設計品質。
116. **ノイズ対シグナル比（Signal-to-Noise Ratio）**: コンテキスト全体の中で、現在の意思決定に直接役立つ有効情報の割合。
117. **AGENTS.md**: プロジェクトの設計方針、ビルド手順、禁止事項をAIエージェント向けに定義するリポジトリ標準の指示ファイル。
118. **CLAUDE.md / GEMINI.md**: 特定のAIコーディングエージェントがセッション開始時に自動読み込みするプロジェクトコンテキスト定義書。
119. **ルールファイル（Project Rules）**: コーディング規約やセキュリティ指針など、常に遵守すべき不変の制約をモジュール化して管理する設定群。
120. **カスタムスキル（SKILL.md）**: 特定タスクの専門手順・チェックリスト・参照スクリプトをパッケージ化し、必要時のみ読み込む知識単位。
121. **階層型コンテキスト（Hierarchical Context）**: グローバル・リポジトリルート・サブディレクトリ単位で粒度の異なるルールを重ね合わせる設計。
122. **コンテキストのスコープ制御（Context Scoping）**: ファイルパターンや作業領域に応じて、適用するルールや知識を自動フィルタリングする仕組み。
123. **リポジトリマップ（Repository Map）**: ファイル一覧・主要クラス・依存関係を簡潔にまとめ、AIの探索コストを最小化する案内図。
124. **フォルダ構造ドキュメント（FolderStructure.md）**: ディレクトリ構成や各モジュールの責務を明記し、AIが毎回全ファイルを走査せずに済むようにする索引。
125. **セッション引き継ぎメモ（Handoff Note）**: セッションを跨いで作業を継続する際、完了事項・未解決課題・次の一手を凝縮した引き継ぎコンテキスト。
126. **作業ログ（Prompt History / Work Log）**: 過去の指示と変更意図を時系列で記録し、再説明コストを削減する継続的コンテキスト。
127. **外部メモリ（External Memory）**: 会話履歴の外にあるMarkdownファイルやDBに設計判断や状態を永続化し、必要なときに再読込する機構。
128. **ワーキングメモリ（Working Memory）**: 現在のタスク遂行中にAIがアクティブに保持・更新する短期的なコンテキスト領域。
129. **長期メモリ（Long-Term Memory）**: ユーザーの好み、アーキテクチャ決定、過去の失敗教訓などを複数セッション横断で保持する知識基盤。
130. **エピソード記憶（Episodic Memory）**: 過去のバグ修正経緯や障害対応の具体的事例を保存し、類似問題発生時に参照させる記憶構造。
131. **セマンティックメモリ（Semantic Memory）**: ドメイン知識、API仕様、社内標準など一般化された事実や概念を構造化して蓄える記憶領域。
132. **手続き記憶（Procedural Memory）**: デプロイ手順やレビュー手順など、具体的な実行ステップやワークフローを定型化した知識。
133. **RAG（Retrieval-Augmented Generation）**: 外部ナレッジベースから関連文書を検索してコンテキストに注入し、根拠ある回答を生成する技術。
134. **ハイブリッド検索（Hybrid Search）**: キーワード一致（BM25）とベクトル類似検索を組み合わせ、仕様書やコードの検索再現率を高める手法。
135. **チャンキング戦略（Chunking Strategy）**: ドキュメントを見出し・関数・意味単位で適切に分割し、検索精度と文脈保持を両立させる設計。
136. **セマンティックチャンキング（Semantic Chunking）**: 固定文字数ではなく文章の意味的な切れ目で分割し、仕様の分断を防ぐチャンク生成手法。
137. **オーバーラップチャンキング（Overlap Chunking）**: 隣接チャンク間で前後の文脈を一部重複させ、境界付近の情報欠落を防ぐ分割技法。
138. **リランキング（Reranking）**: 初期検索で取得した候補文書を専用モデルで再評価し、真に関連度の高い上位情報だけをコンテキストへ投入する工程。
139. **メタデータフィルタリング（Metadata Filtering）**: バージョン・作成日・ドメイン・ステータスなどの属性で検索対象を絞り込み、古い仕様の混入を防ぐ手法。
140. **ナレッジグラフ（Knowledge Graph）**: 要件・エンティティ・API・コンポーネント間の関係性をグラフ構造で表現し、多段階推論を支援する基盤。
141. **GraphRAG**: ナレッジグラフとベクトル検索を融合させ、横断的な影響分析や全体像の把握を強化する検索拡張手法。
142. **ASTベースコンテキスト抽出**: 抽象構文木（AST）を解析して関数シグネチャや型定義だけを抽出し、実装詳細を省いて高密度に構造を伝える手法。
143. **シンボルインデックス（Symbol Index）**: クラス名・関数名・インターフェース定義を索引化し、AIが定義元や参照先を高速に特定できる仕組み。
144. **依存関係グラフ（Dependency Graph）**: モジュールやファイル間の参照関係を可視化し、変更時に読み込むべき関連コンテキストを特定する構造。
145. **コンテキストの鮮度管理（Context Freshness）**: 仕様書やマップが最新コードと乖離していないか検知し、古い情報の参照を防止する運用設計。
146. **バージョニングされたコンテキスト（Versioned Context）**: 要件やルールをGitでコードと同一リポジトリ管理し、時点ごとの整合性を保証する実践。
147. **MCP（Model Context Protocol）**: AIエージェントが外部ツール・DB・ドキュメント基盤へ標準化された手順で安全にアクセスするためのプロトコル。
148. **MCPリソース（MCP Resources）**: MCPサーバー経由でAIに読み取り専用の構造化データや最新仕様を直接提供するデータエンドポイント。
149. **ツール定義コンテキスト（Tool Schema Context）**: AIに提供するツールの説明と引数スキーマを簡潔・明確に設計し、誤呼び出しを防ぐ最適化。
150. **ツールの遅延読み込み（Lazy Tool Loading）**: 全ツールのスキーマを初期コンテキストに載せず、必要なツール群だけを動的にロードしてトークンを節約する機構。
151. **情報アーキテクチャ（Information Architecture）**: AIと人間の双方が迷わず目的の仕様へ到達できるよう、知識の分類・階層・命名を体系化する設計。
152. **タクソノミ設計（Taxonomy Design）**: ドメイン概念やドキュメント種別を階層的に分類し、検索性と一貫性を高める分類体系。
153. **オントロジー設計（Ontology Design）**: 業務領域における概念同士の厳密な関係性・制約・属性を定義する知識モデル。
154. **機械可読性（Machine Readability）**: YAML・JSON・Markdownテーブル・Mermaidなど、LLMやパーサーが誤解なく構造を解釈できる記述品質。
155. **人間可読性（Human Readability）**: レビュアーやステークホルダーが短時間で意図を把握・承認できる見通しの良いドキュメント構造。
156. **デュアルオーディエンス設計（Dual-Audience Design）**: 人間の理解しやすさとAIの解釈精度の両方を同時に満たすドキュメント記述方針。
157. **構造化Markdown（Structured Markdown）**: 見出し階層・箇条書き・コールアウト・表を一貫したルールで用い、AIのパーシング精度を高める記法。
158. **YAMLフロントマター（YAML Frontmatter）**: Markdown先頭にタイトル・タグ・適用対象・更新日などのメタデータを構造化記述する領域。
159. **アンカー情報（Anchor Context）**: 推論全体を通じて常に参照・固定される中核仕様や最重要制約（不変条件）。
160. **参照の局所性（Locality of Reference）**: 関連する仕様・制約・データ定義を近い場所に配置し、AIの文脈照合コストを下げる配置原則。
161. **コンテキストの正規化（Context Normalization）**: 表記ゆれや重複記述を統一し、AIが矛盾したルールを受け取らないように整える処理。
162. **優先順位の明示（Precedence Rules）**: 複数ルールが衝突した際にどれを優先するか（例：セキュリティ＞性能＞便宜性）を明文化した指針。
163. **コンテキスト監査（Context Audit）**: プロジェクト内のルール・ドキュメントの肥大化・陳腐化・矛盾を定期的に点検するメンテナンス活動。
164. **グラウンディング（Grounding）**: AIの生成結果を推測ではなく、実在する仕様書・コード・一次データに根拠づける設計原則。
165. **ハルシネーション抑制設計（Anti-Hallucination Design）**: 不明点は推測せず確認するルールや、一次情報参照の義務付けによって虚偽出力を防ぐ仕組み。
166. **引用必須ルール（Citation Requirement）**: AIの設計判断や回答に対し、根拠となった仕様書やファイル箇所の明示を義務付けるコンテキスト規約。
167. **未知領域の明示（Explicit Unknowns）**: 未決定事項や確認待ち項目を「TBD（To Be Determined）」として明示し、AIの勝手な補完を防ぐ工夫。
168. **ネガティブコンテキスト（Negative Context）**: 「使ってはいけないライブラリ」「変更禁止ファイル」など、回避すべき境界を明示する制約情報。
169. **コンテキストの決定論性（Context Determinism）**: 同じタスクであれば常に同じ必要情報が再現性高くAIへ供給される仕組みの構築。
170. **動的コンテキスト組み立て（Dynamic Context Assembly）**: タスク種別・対象ファイル・エラー内容に応じて最適なコンテキスト群を自動編成するパイプライン。
171. **コンテキストルーター（Context Router）**: ユーザーの要求内容から、参照すべきドキュメント・スキル・サブエージェントを自動振り分けする機構。
172. **ドメイン知識パック（Domain Knowledge Pack）**: 業界規制・会計計算・医療用語など特定領域の専門知識を独立モジュール化した参照資料群。
173. **コードベースオンボーディング資料**: 新規参加のAIエージェントがプロジェクト全体像・規約・起動方法を数分で把握できる導入ドキュメント。
174. **不変条件リスト（Invariants List）**: どのような機能追加やリファクタリングを行っても絶対に破ってはならないシステム全体の法則集。
175. **境界コンテキスト定義（Bounded Context Spec）**: マイクロサービスやモジュールごとに用語の意味やデータ所有権の境界を明記したコンテキスト資料。
176. **クロスリファレンス設計（Cross-Referencing）**: 要件書・API仕様・DB設計書・テスト仕様を相対リンクやIDで相互結合し、追跡性を高める構成。
177. **インデックスドキュメント（Index Document）**: 関連ドキュメントへのリンクと一言要約を一覧化し、AIの探索起点となるディレクトリ目次。
178. **要約ピラミッド（Summary Pyramid）**: 1行要約→段落概要→詳細仕様の多層構造でドキュメントを構成し、タスクに応じた粒度で参照可能にする設計。
179. **差分コンテキスト（Diff Context）**: ファイル全体ではなく変更差分（git diff等）を中心に渡すことで、レビューや修正の焦点を絞る手法。
180. **実行時コンテキスト（Runtime Context）**: 環境変数、OS、依存バージョン、テスト結果など、実行環境固有の事実情報をAIへ正確に伝える枠組み。
181. **エラーコンテキスト（Error Context）**: スタックトレース・再現手順・入力データ・期待動作を構造化して渡し、原因特定の精度を高める情報設計。
182. **テレメトリコンテキスト（Telemetry Context）**: 本番メトリクス、スロークエリ、エラーログの要約を設計改善の入力コンテキストとして活用する手法。
183. **ステートファイル（State File）**: 現在の実装進捗、残タスク、決定済み事項を構造化ファイルで管理し、エージェントの状態を可視化する仕組み。
184. **チェックポイント設計（Checkpointing）**: 長期タスクの要所で中間成果物とコンテキスト要約を保存し、途中からの再開や巻き戻しを可能にする設計。
185. **マルチモーダルコンテキスト（Multimodal Context）**: テキストだけでなくUIモック画像、アーキテクチャ図、画面録画をコンテキストとして統合する手法。
186. **デザインシステムコンテキスト（DESIGN.md）**: カラーパレット、タイポグラフィ、余白規則、コンポーネント方針を明文化しUI生成の一貫性を保つ文書。
187. **セキュリティ境界コンテキスト（Trust Boundary Context）**: 信頼できる内部データと外部からの未検証入力の境界を明示し、プロンプトインジェクションや脆弱性を防ぐ設計。
188. **コンテキストサニタイズ（Context Sanitization）**: 個人情報、APIキー、シークレット情報をコンテキスト投入前に自動マスク・除去する保護処理。
189. **プロンプトインジェクション耐性設計**: 外部文書やユーザー入力をデータ領域として隔離し、AIへのシステム指示として誤解釈させない防御構造。
190. **コンテキストの所有権（Context Ownership）**: 各仕様書やルールファイルの更新責任者とレビューフローを明確にし、放置を防ぐガバナンス。
191. **オンデマンド展開（On-Demand Expansion）**: 初期状態では見出しや概要のみを提示し、AIが必要と判断したセクションだけを読み込む仕組み。
192. **トークンバジェット監視（Token Budget Monitoring）**: セッションやワークフローごとのトークン消費量を計測し、肥大化したコンテキストを検知・改善する運用。
193. **コンテキストのテスト（Context Testing）**: 整備したルールや仕様書を与えた際、AIが期待通りの判断・制約遵守を行うか評価ベンチマークで検証する手法。
194. **スナップショットコンテキスト（Context Snapshot）**: 特定の意思決定やリリース時点のコンテキスト一式を凍結保存し、後から再現・監査できるようにする手法。
195. **コンテキストの脱重複（Context Deduplication）**: 複数ファイルに散在する同一ルールのコピーを排除し、単一参照に統一することで矛盾とトークン浪費を防ぐ作業。
196. **コンテキスト転送プロトコル（Context Handoff Protocol）**: 親エージェントからサブエージェントへ必要最小限かつ十分な前提情報を受け渡す定型フォーマット。
197. **暗黙知の形式知化（Tacit-to-Explicit Conversion）**: 熟練開発者の頭の中にあった判断基準や歴史的経緯を文書化し、AIが参照可能なコンテキストへ変換する活動。
198. **歴史的経緯メモ（Historical Context）**: なぜ既存のコードや仕様が一見不自然な形になっているのかを説明し、AIによる誤った「良かれと思った破壊」を防ぐ記述。
199. **コンテキストの可視化（Context Visualization）**: AIに実際に渡されているファイル・ルール・トークン内訳を可視化し、設計の偏りを診断するアプローチ。
200. **コンテキストライフサイクル管理**: コンテキストの作成・検証・活用・圧縮・アーカイブ・廃棄までを一貫して管理する運用プロセス。

## 3. プロンプト設計・指示構造化（201〜300）

201. **プロンプトエンジニアリング（Prompt Engineering）**: AIから意図した品質・形式・制約遵守の出力を安定的に引き出すための指示設計技術。
202. **システムプロンプト（System Prompt）**: AIの役割、基本方針、禁止事項、出力形式などセッション全体を通じて最優先で適用される基盤指示。
203. **ユーザープロンプト（User Prompt）**: 個別のタスク実行時に具体的な目的・対象・入力データ・完了条件を伝える指示文。
204. **構造化プロンプト（Structured Prompt）**: XMLタグやMarkdown見出しで役割・前提・手順・制約・出力形式を明確に区切った指示設計。
205. **XMLタグ構造化（XML Tagging）**: `<context>` `<instructions>` `<constraints>` のように意味ブロックをタグで囲み、LLMの境界認識を高める記法。
206. **ロールプロンプティング（Role Prompting）**: 「シニアアーキテクト」「セキュリティ監査官」など専門的な立場を与え、判断視点と出力基準を揃える手法。
207. **Few-Shotプロンプティング**: 期待する入出力の具体例を数件提示し、AIにフォーマットや判断基準を正確に模倣させる技法。
208. **Zero-Shotプロンプティング**: 具体例を与えずに明確なルールと定義だけでタスクを遂行させる簡潔な指示方式。
209. **One-Shotプロンプティング**: 代表的な成功例を1件だけ示し、トークンを抑えつつ出力構造とトーンを統一する技法。
210. **Chain-of-Thought（CoT）**: 最終結論の前に思考過程や検証ステップを段階的に展開させ、複雑な設計判断の精度を高める手法。
211. **Tree-of-Thoughts（ToT）**: 複数の設計案や分岐を木構造で探索・評価し、最適解を選択させる高度な推論プロンプト設計。
212. **ReActパターン（Reason + Act）**: 推論（思考）と行動（ツール実行・観察）を交互に繰り返し、事実に基づいて要件調査や設計を進める枠組み。
213. **メタプロンプティング（Meta-Prompting）**: AI自身にタスク要件を分析させ、より高精度なプロンプトや仕様テンプレートを生成・改善させる手法。
214. **指示の階層化（Instruction Hierarchy）**: システム指示・開発者規約・ユーザー入力・外部データの優先順位を明確にし、指示衝突を解決する構造。
215. **出力スキーマ指定（Structured Outputs）**: JSON Schemaや型定義を指定し、AIの回答を機械処理可能な厳密フォーマットへ強制する技術。
216. **制約ベースプロンプティング（Constraint-Based Prompting）**: やるべきことだけでなく「変更禁止範囲」「禁止パターン」「文字数制限」を明記して逸脱を防ぐ手法。
217. **ポジティブフレーミング（Positive Framing）**: 「〜するな」だけでなく「代わりに〜せよ」と望ましい行動を具体的に示す指示表現。
218. **ネガティブ制約（Negative Constraints）**: セキュリティ違反や破壊的操作など、絶対に実行してはならない行為を明確に禁止するガードレール指示。
219. **完了条件の明文化（Explicit Completion Criteria）**: 何が検証・達成されたらタスク完了とみなすかを具体的に定義し、中途半端な終了を防ぐ指示要素。
220. **反復的明確化（Iterative Clarification）**: 曖昧な要件をそのまま実装させず、AIから先に確認質問を列挙させて前提を固める対話パターン。
221. **インタビュー型プロンプト（Interview Pattern）**: AIに要件定義のインタビュアー役を担わせ、1問ずつ深掘りして仕様を網羅的に引き出す手法。
222. **ソクラテス式プロンプティング**: 問いかけを通じて設計の前提・矛盾・見落としを人間自身に気づかせる対話的レビュー技法。
223. **自己批判プロンプト（Self-Critique / Reflection）**: 生成した仕様や設計案をAI自身に批判的視点で再点検させ、欠陥を自律修正させる手法。
224. **敵対的レビュー（Adversarial Review / Red-Teaming Prompt）**: 攻撃者や批判的レビュアーの視点で仕様の抜け穴・エッジケース・脆弱性を意図的に探させる指示。
225. **マルチペルソナ検討（Multi-Persona Deliberation）**: PM・エンジニア・QA・SREなど複数視点からの意見を並列に生成させ、バランスの良い仕様へ収束させる手法。
226. **プロンプトテンプレート（Prompt Template）**: 要件定義・設計レビュー・API仕様作成など頻出作業を再利用可能な変数付きテンプレートとして標準化した資産。
227. **プロンプトチェーン（Prompt Chaining）**: 巨大なタスクを「抽出→構造化→検証→生成」の複数プロンプトへ分割し、出力を次段へ繋ぐパイプライン設計。
228. **プロンプトのモジュール化（Modular Prompting）**: 共通ルール・出力形式・ドメイン知識を部品化し、タスクごとに組み合わせて保守性を高める設計。
229. **プロンプトバージョン管理（Prompt Versioning）**: 重要なシステム指示やテンプレートをGitで履歴管理し、精度変化を追跡・ロールバックできる運用。
230. **プロンプト評価（Prompt Evaluation / Evals）**: 代表的なテストケース群に対してプロンプトの正確性・網羅性・一貫性を定量評価する仕組み。
231. **LLM-as-a-Judge**: 別の評価用LLMと明確なルーブリックを用いて、仕様書や設計案の品質を自動採点する検証手法。
232. **評価ルーブリック（Evaluation Rubric）**: 網羅性・一貫性・具体性・実現可能性など、出力品質を段階評価するための明文化された採点基準。
233. **ゴールデンデータセット（Golden Dataset）**: プロンプト改善時に回帰劣化が起きていないか検証するための高品質な基準入出力セット。
234. **プロンプト回帰テスト（Prompt Regression Testing）**: 指示文の修正によって既存ユースケースの精度や制約遵守が崩れていないか確認するテスト。
235. **デリミタ設計（Delimiter Design）**: 三重バッククォートや区切り線を用い、指示文と引用対象データ・コードを明確に分離する記法。
236. **アンカリングバイアス対策**: 最初の仮説や例示にAIが過剰に引きずられないよう、複数案比較やゼロベース検討を促すプロンプト工夫。
237. **迎合バイアス対策（Anti-Sycophancy Prompting）**: AIがユーザーの誤った前提に無批判に同調せず、技術的根拠に基づき反論・指摘するよう促す指示。
238. **不確実性の表明指示（Uncertainty Calibration）**: 確信が持てない情報や仕様の空白を推測で埋めず、「不明・要確認」と明示させる指示設計。
239. **ステップバイステップ検証指示**: 仕様作成後に要件ID・制約・異常系のチェックリストを1項目ずつ照合させる確認プロンプト。
240. **チェックリスト駆動プロンプティング**: 事前に定義した品質チェックリストをプロンプトへ組み込み、見落としを構造的に防ぐ手法。
241. **対照例示（Contrastive Examples / Good vs. Bad）**: 良い仕様例と悪い仕様例を並べて提示し、境界判断の解像度を高めるプロンプト技法。
242. **エッジケース列挙プロンプト**: 正常系だけでなく境界値・競合状態・権限エラー・部分失敗を体系的に洗い出させる専門指示。
243. **抽象度制御（Abstraction Level Control）**: 概念設計・論理設計・物理設計など、出力すべき詳細度のレベルを明示して過剰・不足を防ぐ指示。
244. **トーン＆スタイル指定（Tone & Style Guidelines）**: 断定表現の統一、専門用語の扱い、簡潔さなどドキュメント全体の文体品質を揃える指定。
245. **言語・ロケール指定（Language & Locale Specification）**: 出力言語、日付形式、通貨表記、技術用語の原語併記ルールなどを規定するプロンプト設定。
246. **思考と出力の分離（Reasoning-Output Separation）**: 内部の比較検討プロセスと最終成果物（仕様書本体）を明確に分け、成果物の可読性を保つ設計。
247. **プロンプトインジェクション防御指示**: 外部参照テキスト内に含まれる命令文を無視し、あくまで解析対象データとして扱うよう明記する防御策。
248. **前提確認ゲート（Pre-Execution Gate）**: 実装や大幅な変更に進む前に、解釈した要件と計画を提示して人間承認を得る停止ポイント指示。
249. **計画先行プロンプト（Plan-First Prompting）**: いきなりコードや詳細文書を書かせず、先に全体構成・方針・影響範囲の計画を立案させる手順。
250. **段階的詳細化プロンプト（Stepwise Refinement）**: 骨子（アウトライン）→セクション詳細→エッジケース補完の順に解像度を上げていく指示戦略。
251. **差分更新指示（Incremental Diff Prompting）**: 文書全体を再生成させず、変更が必要な箇所だけをピンポイントで更新させて意図せぬ改変を防ぐ手法。
252. **逆算プロンプティング（Backward Prompting）**: 最終的に必要なテストケースや受け入れ基準から逆算して、不足している要件や入力仕様を特定する手法。
253. **仮説検証プロンプト（Hypothesis-Driven Prompting）**: 設計上の疑問を仮説として言語化し、コード調査やログ確認によって反証・裏付けを行わせる指示。
254. **トレードオフ分析プロンプト**: 単一解を即答させず、複数案のメリット・デメリット・コスト・リスクを比較表で整理させる設計指示。
255. **制約充足プロンプト（Constraint Satisfaction Prompting）**: 性能・コスト・納期・互換性など複数の制約条件をすべて満たす解空間を探索させる指示。
256. **要約粒度指定（Summarization Granularity）**: 経営層向け3行要約、開発者向け変更点一覧など、読み手に応じた圧縮率と着眼点を指定する手法。
257. **抽出プロンプト（Extraction Prompting）**: 議事録・チャット履歴・既存資料から機能要件・決定事項・未決課題を構造化抽出する指示設計。
258. **正規化プロンプト（Normalization Prompting）**: 複数人から集まった雑多な要望を統一フォーマット・統一用語の要件リストへ整形する指示。
259. **矛盾検出プロンプト（Contradiction Detection Prompting）**: 複数の仕様書や要件項目を突き合わせ、論理的矛盾や用語の食い違いを自動発見させる指示。
260. **抜け漏れ検査プロンプト（Completeness Audit Prompting）**: CRUD操作、権限マトリクス、異常系、非機能要件の観点から仕様の欠落を網羅診断させる指示。
261. **依存関係抽出プロンプト**: 要件群から実装順序の制約やブロッカーとなる先行タスクを自動抽出し、実行計画へ繋げる指示。
262. **見積もり支援プロンプト**: 要件の複雑さ・不確実性・影響ファイル数から相対規模（Tシャツサイズ等）とリスク要因を整理させる指示。
263. **用語統一プロンプト（Terminology Alignment）**: 用語集に基づき、仕様書内の表記ゆれや別名表現を正規のユビキタス言語へ置換・統一する指示。
264. **スキーマ生成プロンプト**: 自然言語のビジネス要件からJSON Schema、SQL DDL、OpenAPI、TypeScript型定義へ変換する指示設計。
265. **テスト観点生成プロンプト**: 要件定義書から同値分割・境界値分析・状態遷移テストの観点一覧を網羅生成させる指示。
266. **ユーザー視点シミュレーション**: 特定のペルソナとして仕様書や画面フローを疑似体験させ、UX上の違和感や迷いを洗い出す手法。
267. **障害シナリオ生成（Failure Mode Prompting）**: ネットワーク断・タイムアウト・二重送信・DBロックなど障害発生時の挙動漏れを炙り出す指示。
268. **セキュリティ脅威モデリングプロンプト**: STRIDE等の枠組みに沿って、要件段階から認証回避・権限昇格・情報漏洩リスクを洗い出す指示。
269. **出力長・密度制御（Length & Density Control）**: 箇条書き1項目あたりの文数や最大文字数を規定し、冗長な水増し出力を抑制するプロンプト設計。
270. **決定事項の固定（Decision Anchoring）**: 合意済みの設計判断をプロンプト冒頭に固定し、後続の議論でAIが勝手に覆さないようにする技法。
271. **フォールバック指示（Fallback Instruction）**: 情報不足やツール失敗時に勝手な推測へ走らず、どの代替手順やエスカレーションを取るか明示する指示。
272. **スコープ境界指示（Scope Guardrail）**: 「このタスクでは認証仕様のみ扱い、課金仕様は変更しない」と作業境界を厳密に区切る指示。
273. **ツール使用方針指示（Tool Use Policy）**: いつファイルを読むか、いつ検索するか、いつユーザーへ確認するかの行動優先度を規定する指示。
274. **並列調査指示（Parallel Exploration Prompting）**: 独立した複数の観点（既存コード・API仕様・DBスキーマ等）を同時に調査させ、待機時間を短縮する指示。
275. **サブエージェント委譲ブリーフ（Delegation Brief）**: サブエージェントに独立タスクを渡す際、目的・所有範囲・制約・完了条件を過不足なく伝える指示書。
276. **オーケストレーション指示（Orchestration Prompt）**: 複数エージェントの役割分担・成果物統合・品質検証の流れを制御する統括プロンプト。
277. **コンテキスト参照指示（Context Grounding Prompt）**: 「回答前に必ず `Docs/FolderStructure.md` と関連仕様を読むこと」と一次情報確認を義務付ける指示。
278. **禁止語・曖昧語フィルタ指示**: 「適切に」「柔軟に」「必要に応じて」といった曖昧表現の使用を禁じ、具体条件へ書き換えさせる指示。
279. **バージョン差分比較プロンプト**: 旧仕様書と新仕様書の変更点を抽出し、影響を受けるAPI・データ・テストを一覧化させる指示。
280. **ドメイン翻訳プロンプト**: ビジネス側の要望を技術仕様へ、または技術制約をビジネス側の意思決定言語へ相互翻訳する指示設計。
281. **マイクロプロンプティング（Micro-Prompting）**: 1回の指示に複数目的を詰め込まず、単一責任の小さく明快な指示を連鎖させて精度を高める手法。
282. **マクロプロンプティング（Macro-Prompting）**: 明確な仕様書とチェックリストを揃え、自律エージェントへ大きな成果物生成を一括委譲する指示設計。
283. **プロンプトのLint（Prompt Linting）**: 矛盾する指示、曖昧な表現、冗長な重複、抜け落ちた出力条件を機械的に点検する品質管理手法。
284. **プロンプトのA/Bテスト**: 2つの指示設計案を同一の要件タスク群で比較実行し、精度・トークン効率・安定性を定量検証する手法。
285. **温度パラメータ設計（Temperature Tuning）**: 要件の厳密検証では低温（決定論的）、アイデア発散では中温といった目的に応じた生成多様性の制御。
286. **プロンプトライブラリ（Prompt Library）**: チーム全体で検証済みの要件定義・設計レビュー・ドキュメント生成プロンプトを共有管理する資産庫。
287. **スラッシュコマンド設計（Slash Commands）**: よく使う定型プロンプトワークフロー（`/plan` `/grill-me`等）を短いコマンド名で即時呼び出せるようにする仕組み。
288. **対話プロトコル設計（Interaction Protocol）**: AIが質問する形式（選択肢提示、推奨案の明示など）を標準化し、人間の意思決定負荷を下げる設計。
289. **推奨案先行提示（Recommendation-First Pattern）**: 選択肢を並べるだけでなく、理由付きの推奨案を先頭に提示させて合意形成を高速化する指示パターン。
290. **前提リスト化（Assumption Listing）**: AIが作業を進める際に置いた仮定を必ず一覧出力させ、認識ズレを早期発見するプロンプト習慣。
291. **未解決事項トラッキング指示**: 仕様作成中に判明した未決定項目を `Open Questions` セクションへ自動集約させる出力構造ルール。
292. **変更理由の明記指示（Rationale Prompting）**: 設計提案や仕様修正のたびに「なぜその選択をしたか」の根拠を必ず併記させる指示。
293. **コード例と仕様の分離指示**: 仕様定義段階では実装コードの詳細に踏み込みすぎず、インターフェースと振る舞い契約に集中させる制御指示。
294. **テスト可能性チェック指示（Testability Check）**: 記述したすべての要件について「自動テストで検証可能か」を自己判定させる品質強化プロンプト。
295. **後方互換性チェック指示**: 仕様変更時に既存のクライアントや保存済みデータが壊れないかを必ず確認させる防御的プロンプト。
296. **データプライバシー点検指示**: 新規要件が個人情報や機密データを扱う場合、保存期間・暗号化・削除権の仕様漏れを自動確認させる指示。
297. **多言語整合性指示**: 日本語仕様と英語の識別子・API名・エラーコードの対応関係を一貫させる命名・記述ルール指示。
298. **プロンプトの簡潔化（Prompt Compression / Distilling）**: 試行錯誤で肥大化した指示文から不要な修飾を削ぎ落とし、核心ルールだけを残すリファクタリング。
299. **指示ドリフト検知（Instruction Drift Detection）**: 長い対話の中でAIが初期の制約やフォーマットから逸脱していないかを定期監視・再注入する手法。
300. **プロンプト設計標準（Prompt Style Guide）**: チームや組織内でプロンプト・ルールファイル・スキルを書く際の構造・記法・レビュー基準を定めた指針。

## 4. ドメインモデリング・アーキテクチャ設計（301〜400）

301. **ドメイン駆動設計（DDD: Domain-Driven Design）**: 業務ドメインの概念とルールを設計・コードの中心に据え、AIと人間の共通理解を保つ設計手法。
302. **ユビキタス言語（Ubiquitous Language）**: 企画・開発・仕様書・コード・AIプロンプトのすべてで統一して使うドメイン固有の共通語彙。
303. **境界づけられたコンテキスト（Bounded Context）**: 特定のドメインモデルと用語が一貫した意味を持つ明確な論理境界。
304. **コンテキストマップ（Context Map）**: 複数の境界づけられたコンテキスト間の依存関係・統合方式・力関係を俯瞰する設計図。
305. **コアドメイン（Core Domain）**: ビジネスの競争優位性を生み出し、最も手厚い要件定義と設計投資を行うべき中核領域。
306. **サブドメイン（Subdomain）**: ビジネス全体を構成する機能領域をコア・支援・汎用に分類し、自作か外部利用かを判断する枠組み。
307. **エンティティ（Entity）**: 属性が変化しても一意の識別子によって同一性が追跡されるドメインオブジェクト。
308. **値オブジェクト（Value Object）**: 金額・メールアドレス・期間など、属性値そのものが意味を持ち不変（Immutable）として扱うドメインモデル。
309. **集約（Aggregate）**: データ整合性とビジネスルールを一体で保証するエンティティと値オブジェクトのトランザクション境界。
310. **集約ルート（Aggregate Root）**: 集約外部からのアクセス窓口を単一オブジェクトに限定し、不変条件を保護する設計要素。
311. **ドメインイベント（Domain Event）**: 「注文確定」「決済完了」など、業務上重要な出来事の発生を過去形で表現する疎結合連携モデル。
312. **ドメインサービス（Domain Service）**: 単一のエンティティや値オブジェクトに属さない複数のドメイン概念を跨ぐ業務ロジックの受け皿。
313. **リポジトリパターン（Repository Pattern）**: 永続化層の詳細を隠蔽し、ドメイン層からコレクションのように集約を取得・保存する抽象インターフェース。
314. **腐敗防止層（ACL: Anti-Corruption Layer）**: 外部システムやレガシー基盤の歪んだモデルが自システムのドメイン設計へ侵入するのを防ぐ変換層。
315. **イベントストーミング（Event Storming）**: ドメインイベントを時系列に並べて業務フロー・コマンド・集約・課題を全員で発見するモデリング手法。
316. **イベントモデリング（Event Modeling）**: 画面・コマンド・イベント・ビューを時間軸で一直線に並べ、システム仕様を設計図化する手法。
317. **関心の分離（SoC: Separation of Concerns）**: UI・ビジネスロジック・インフラなど役割ごとに責務を明確分離し、AIの変更影響範囲を局所化する原則。
318. **クリーンアーキテクチャ（Clean Architecture）**: 依存の方向を外側から内側のドメイン層へ統一し、フレームワークやDBから独立した設計を保つ構造。
319. **ヘキサゴナルアーキテクチャ（ポート＆アダプタ）**: コアロジックをポート（インターフェース）で囲み、外部I/Oをアダプタとして差し替え可能にする設計。
320. **オニオンアーキテクチャ（Onion Architecture）**: ドメインモデルを中心核とし、同心円状にアプリケーション層・インフラ層を配置する依存逆転構造。
321. **レイヤードアーキテクチャ（Layered Architecture）**: プレゼンテーション・アプリケーション・ドメイン・インフラの階層に責務を分割する基本構成。
322. **モジュラーモノリス（Modular Monolith）**: 単一デプロイ単位を保ちながら内部を明確な境界モジュールに分割し、保守性と開発速度を両立する構成。
323. **マイクロサービスアーキテクチャ**: 独立デプロイ可能な小規模サービス群へ分割し、組織・スケーリングの自律性を高める分散設計。
324. **CQRS（コマンドクエリ責務分離）**: データ更新（Command）と参照（Query）のモデル・経路を分離し、複雑な要件と読取性能を両立する設計。
325. **イベントソーシング（Event Sourcing）**: 最新状態ではなく状態変化をもたらした全イベント履歴を正として保存し、監査性と再現性を高める方式。
326. **API契約設計（API Contract Design）**: エンドポイント、リクエスト/レスポンス型、ステータスコード、エラー形式を厳密に定義するインターフェース設計。
327. **OpenAPI仕様（OAS）**: REST APIの構造をYAML/JSONで機械可読に定義し、AIによるコード生成・モック・検証の起点とする標準仕様。
328. **GraphQLスキーマ設計**: クライアントが必要なデータを型安全に宣言取得できるよう、型・クエリ・ミューテーションを定義する設計。
329. **gRPC / Protocol Buffers設計**: 厳密なバイナリスキーマ（`.proto`）により高速・型安全なサービス間通信契約を定義する手法。
330. **AsyncAPI仕様**: KafkaやWebSocketなど非同期イベント駆動APIのチャネル・メッセージ構造を標準記法で定義する仕様。
331. **エラーハンドリング規約（Error Contract）**: RFC 9457（Problem Details）等に準拠し、エラーコード・メッセージ・再試行可否を統一する設計。
332. **冪等性設計（Idempotency Design）**: 同一リクエストが重複実行されても結果が1回実行と変わらないよう冪等キー等で保証する信頼性設計。
333. **整合性モデル（Consistency Model）**: 強整合性が必要か結果整合性で許容できるかを要件ごとに明確化するデータ設計判断。
334. **トランザクション境界設計**: どの操作群を原子的にコミット・ロールバックすべきかを定義し、データ不整合を防ぐ設計。
335. **Sagaパターン**: 分散システム間で複数サービスに跨る業務トランザクションを補償処理（ロールバック）付きで制御する設計。
336. **Outboxパターン**: DB更新とイベント発行を同一トランザクションで記録し、メッセージ欠損を防ぐ信頼性連携パターン。
337. **データモデリング（Data Modeling）**: 概念モデル・論理モデル・物理モデルの3段階でビジネスデータを構造化する設計工程。
338. **ER図（Entity-Relationship Diagram）**: エンティティ間の1対多・多対多関係や主キー・外部キー制約を視覚化するデータ設計図。
339. **正規化と非正規化（Normalization / Denormalization）**: データ重複排除による整合性確保と、読取性能向上のための意図的冗長化のトレードオフ設計。
340. **スキーマ進化戦略（Schema Evolution）**: 無停止でカラム追加・型変更・廃止を行うためのExpand-Contractパターン等の互換性設計。
341. **マルチテナンシー設計（Multi-Tenancy Design）**: 複数顧客のデータを共有DB・スキーマ分離・DB分離のどの方式で安全に隔離するか決める設計。
342. **認可モデル設計（Authorization Model）**: RBAC・ABAC・ReBACなど、誰がどのリソースへ何の操作を行えるかを定義するアクセス制御設計。
343. **認証フロー設計（Authentication Flow）**: OAuth 2.0、OIDC、パスキー、セッション管理など本人確認とトークンライフサイクルの設計。
344. **ゼロトラスト設計原則（Zero Trust Architecture）**: 内部ネットワークであっても暗黙に信頼せず、すべてのアクセスを検証・最小権限化するセキュリティ設計。
345. **データライフサイクル設計**: データの生成・保存・アーカイブ・匿名化・完全削除（論理削除 vs 物理削除）までの規則定義。
346. **監査ログ設計（Audit Trail Design）**: 「誰が・いつ・何を・どう変更したか」を改ざん耐性を持って記録するコンプライアンス設計。
347. **状態機械設計（Finite State Machine）**: 注文・承認・決済などの複雑な状態遷移を有限状態機械として厳密定義し、不正状態を防ぐ手法。
348. **ワークフローエンジン設計**: 長時間実行・人手承認・再試行を伴う業務プロセスをオーケストレーションする設計構造。
349. **キャッシュ戦略設計（Caching Strategy）**: どのデータをどの層（CDN・アプリ・DB）にどれだけのTTLと無効化規則でキャッシュするかの設計。
350. **レート制限・バックプレッシャー設計**: 過剰トラフィックからシステムを保護するための制限値・優先度制御・キューイング仕様。
351. **サーキットブレーカー設計**: 外部依存障害の連鎖を防ぐため、異常検知時に即時遮断・フォールバックを行う耐障害設計。
352. **グレースフルデグラデーション（Graceful Degradation）**: 一部機能や外部APIが停止しても、中核機能を縮退状態で継続提供できるようにする可用性設計。
353. **C4モデル（Context, Containers, Components, Code）**: システム全体像から内部コンポーネントまで4段階のズームレベルでアーキテクチャを可視化する記法。
354. **システムコンテキスト図（System Context Diagram）**: 対象システムと外部ユーザー・外部連携システムの関係性を最上位視点で示す図。
355. **コンテナ図（Container Diagram）**: Webアプリ、APIサーバー、DB、メッセージキューなど実行単位の構成と通信プロトコルを示す図。
356. **コンポーネント図（Component Diagram）**: コンテナ内部の主要モジュールと責務分担・依存方向を整理した詳細設計図。
357. **シーケンス図（Sequence Diagram）**: アクターやコンポーネント間のメッセージ送受信を時系列で表現し、同期・非同期処理の流れを明示する図。
358. **データフロー図（DFD: Data Flow Diagram）**: 入力から変換・保存・出力までのデータの流れと信頼境界を可視化する分析図。
359. **アーキテクチャ決定記録（ADR: Architecture Decision Record）**: 重要な設計選択の背景・検討案・決定理由・トレードオフを不変の記録として残す文書。
360. **RFC（Request for Comments）**: 大規模な設計変更や技術選定に先立ち、背景・提案・代替案を共有して合意を得る設計提案書。
361. **技術設計書（TDD / Design Doc）**: 要件を実現するための具体的なシステム構造、データスキーマ、API、移行計画、リスク対策をまとめた文書。
362. **フィットネス関数（Architectural Fitness Functions）**: 依存関係ルールや性能基準など、アーキテクチャ品質が崩れていないかを自動検証する仕組み。
363. **依存性逆転の原則（DIP）**: 上位のビジネス方針が下位の技術詳細に依存しないよう、抽象インターフェースを介して結合する設計原則。
364. **単一責任の原則（SRP）**: 1つのモジュールやクラスが変更される理由を1つに限定し、AIによる局所修正を安全にする原則。
365. **インターフェース分離の原則（ISP）**: 巨大な汎用インターフェースを避け、利用側の目的に特化した小さく明確な契約に分割する原則。
366. **疎結合・高凝集（Loose Coupling, High Cohesion）**: 関連要素を1か所にまとめつつ他モジュールとの依存を最小化し、変更耐性を高める基本原則。
367. **契約による設計（DbC: Design by Contract）**: 事前条件・事後条件・不変条件を明示し、コンポーネント間の責任境界を明確化する設計思想。
368. **型駆動設計（Type-Driven Design）**: 不正な状態を型システム上で表現不能（Make Illegal States Unrepresentable）にし、AIの実装バグを防ぐ手法。
369. **スキーマファースト設計（Schema-First Design）**: ZodやJSON Schema等でデータ構造とバリデーションを最初に定義し、型・ドキュメント・検証を一元化する手法。
370. **入力バリデーション境界設計**: システム外部境界で厳密に検証・サニタイズを行い、内部ドメイン層では信頼済みデータのみ扱う設計。
371. **アンチパターン回避設計**: 巨大な泥団子（Big Ball of Mud）や利口なUI（Smart UI）をルール化し、AIの安易な密結合実装を防ぐ指針。
372. **技術選定マトリクス（Tech Selection Matrix）**: 学習コスト・保守性・エコシステム・AIのコード生成適性など多軸で技術スタックを評価比較する表。
373. **AIフレンドリーアーキテクチャ**: 小さなファイル粒度、明示的な型、予測可能なディレクトリ構造によりAIの理解・変更精度を最大化する設計。
374. **コロケーション設計（Colocation）**: 関連するコンポーネント・スタイル・テスト・仕様を近いディレクトリへ配置し、AIの探索範囲を狭める構造。
375. **プラグイン／拡張ポイント設計**: 将来の機能追加をコア改変なしで行えるよう、明確なフックやインターフェース境界を用意する設計。
376. **設定とコードの分離（Externalized Configuration）**: 環境依存値や機能切替パラメータをコードから分離し、安全に環境展開できる12-Factor設計。
377. **ステートレス設計（Stateless Architecture）**: アプリケーションサーバー側にセッション状態を保持せず、水平スケールと障害復旧を容易にする設計。
378. **非同期ジョブ設計（Async Job Architecture）**: 重い処理や外部連携をバックグラウンドキューへ逃がし、応答性と再試行耐性を確保する設計。
379. **Webhook設計**: 外部サービスとのイベント通知連携において、署名検証・再送制御・順序逆転対策を含めて規定する設計。
380. **バージョニング戦略（API / Schema Versioning）**: URLパス・ヘッダー・フィールド非推奨化など、破壊的変更を安全に吸収するバージョン管理設計。
381. **ストラングラーフィグパターン（Strangler Fig）**: レガシーシステムを一括置換せず、機能単位で段階的に新アーキテクチャへ置き換える移行設計。
382. **デッドレターキュー設計（DLQ）**: 規定回数の再試行でも処理失敗したメッセージを退避・調査・再実行できるようにする運用設計。
383. **観測ポイント設計（Instrumentation Design）**: 要件段階から構造化ログ項目、ビジネスメトリクス、分散トレースIDの伝播方針を組み込む設計。
384. **コスト認識アーキテクチャ（FinOps-Aware Design）**: クラウド課金やLLM推論トークンコストを設計制約として織り込み、過剰コストを未然に防ぐ設計。
385. **マルチリージョン・DR設計**: 地理的冗長化やフェイルオーバー方針をRPO/RTO要件に合わせて設計する災害対策アーキテクチャ。
386. **LLMオーケストレーション設計**: 単一モデル呼び出し・ワークフロー・自律エージェントのどの制御パターンを業務要件に採用するかの設計。
387. **ツール境界設計（Agent Tool Boundaries）**: AIエージェントに与える読み取り・書き込み・外部実行権限を最小権限原則で分離する設計。
388. **Human-in-the-Loop（HITL）設計**: 不可逆操作や高リスク判断の直前に人間承認ステップを挟む安全なエージェント業務設計。
389. **決定論的処理と確率的処理の分離**: 金額計算や権限判定は決定論的コードに任せ、要約や分類のみをLLMへ委ねるハイブリッド設計。
390. **ガードレールアーキテクチャ（Guardrail Architecture）**: AI入出力の前後に検証・フィルタ・ポリシーチェック層を配置し安全性を担保する構造。
391. **フォールバックモデル設計**: 推論API障害やレート制限時に代替モデルやルールベース処理へ安全に退避する信頼性設計。
392. **評価パイプライン設計（Evaluation Architecture）**: 本番前の品質検証と本番後の継続モニタリングをデータ駆動で回すAI品質保証基盤の設計。
393. **データガバナンス設計**: データの所有権、機密区分、利用許諾、学習利用の可否をアーキテクチャレベルで統制する設計。
394. **プライバシーバイデザイン（Privacy by Design）**: 企画・要件定義の初期段階からデータ最小化・暗号化・匿名化をアーキテクチャへ組み込む原則。
395. **セキュリティバイデザイン（Security by Design）**: 後付けの対策ではなく、脅威モデルと防御層を初期設計の中核に組み込む開発アプローチ。
396. **アクセシビリティバイデザイン**: セマンティック構造、キーボード操作、コントラスト基準をUI要件・設計の初期から組み込むアプローチ。
397. **フロントエンド状態管理設計**: サーバー状態・UIローカル状態・URL状態の責務を分離し、画面の不整合を防ぐクライアント設計。
398. **コンポーネント階層設計**: デザインシステムに基づき、プリミティブ・複合コンポーネント・ページ構成の再利用境界を定義するUI設計。
399. **デザイン・トゥ・コード整合性（Design-to-Code Alignment）**: デザイントークンやコンポーネント仕様をコード側と1対1対応させ、UI実装のズレを防ぐ設計。
400. **アーキテクチャレビュー（Architecture Review）**: 実装着手前にスケーラビリティ・セキュリティ・保守性・コストの妥当性を多角検証する設計関門。

## 5. ドキュメント管理・プロトタイピング・合意形成（401〜500）

401. **Docs-as-Code**: 仕様書や設計書をコードと同じGitリポジトリ・PRレビュー・CIチェックで管理するドキュメント運用手法。
402. **実装ロードマップ（ImplementationRoadmap.md）**: フェーズ別の目標・依存順序・マイルストーンを整理し、AIと人間が進捗と次工程を共有する計画書。
403. **仕様変更ログ（Spec Changelog）**: 要件や仕様の追加・変更・廃止を日付と理由付きで時系列記録し、認識ズレを防ぐ変更履歴。
404. **Mermaid図表記法**: テキストベースでフローチャート・シーケンス図・ER図・状態遷移図を記述し、Git差分管理とAI生成を両立する記法。
405. **PlantUML**: テキスト記述からUML図を自動生成し、設計仕様の視覚化とバージョン管理を統合するダイアグラムツール。
406. **ワイヤーフレーム（Wireframe）**: 装飾を省いて画面の情報配置・導線・機能要素を素早く合意するための低忠実度UI設計図。
407. **インタラクティブプロトタイプ**: クリックや画面遷移を実際に操作できる試作品を用い、要件の違和感を実装前に検証する手法。
408. **AI高速プロトタイピング（Rapid AI Prototyping）**: 要件定義の初期段階でAIに動くUIモックを数分で生成させ、抽象的な認識ズレを即座に解消する手法。
409. **使い捨てプロトタイプ（Throwaway Prototype）**: 本番コードへ流用せず、仕様検証や合意形成のためだけに作って破棄することを前提とした試作。
410. **進化的プロトタイプ（Evolutionary Prototype）**: 検証を通過した試作を土台に、品質要件やテストを段階的に肉付けして本番へ育てるアプローチ。
411. **ストーリーボード（Storyboard）**: ユーザーの利用シーンと画面変化をコマ割りで描き、体験全体の流れをステークホルダーと共有する手法。
412. **ユーザーストーリーマッピング**: ユーザー行動を横軸、リリース優先度を縦軸に並べ、MVPと後続リリースの全体像を合意する手法。
413. **デザインスプリント（Design Sprint）**: 課題定義から試作・ユーザーテストまでを数日で一気に回し、要件の妥当性を高速検証するプロセス。
414. **ディスカバリーフェーズ（Product Discovery）**: 「何を正しく作るか」を見極めるため、ユーザー調査・仮説検証・試作を行う要件定義前段の活動。
415. **デリバリーフェーズ（Product Delivery）**: 合意された仕様に基づき、安定した品質と速度で設計・実装・リリースを行う実行フェーズ。
416. **デュアルトラックアジャイル（Dual-Track Agile）**: 要件探索（ディスカバリー）と実装（デリバリー）を並行推進し、常に検証済みの仕様を供給する体制。
417. **ステークホルダー分析（Stakeholder Analysis）**: 意思決定者・利用者・運用者・法務など関係者の関心事と影響度を整理し、要件漏れを防ぐ手法。
418. **RACIマトリクス**: 各要件や設計決定における実行責任・説明責任・相談先・報告先を明確にする役割分担表。
419. **合意形成（Consensus Building）**: 利害の異なる関係者間で優先順位・トレードオフ・非対象範囲について明確な納得と承認を得る活動。
420. **サインオフ（Sign-off）**: 要件定義書や設計書の確定版に対して責任者が正式承認を与え、実装フェーズへの移行を確定する手続き。
421. **デザインレビュー（Design Review）**: UI・UX・システム設計の妥当性を多職種で検証し、手戻りを未然に防ぐレビュー会議または非同期プロセス。
422. **非同期レビュー（Asynchronous Review）**: PRやドキュメントコメント上で時間差を許容しながら議論・合意形成を行うリモート適合型のレビュー運用。
423. **決定ログ（Decision Log）**: 会議やチャットで決まった事項・決定者・日時・理由を一元記録し、議論の蒸し返しを防ぐ一覧表。
424. **未決課題リスト（Open Questions / Issue Log）**: 仕様確定のために回答が必要な疑問点・担当者・期限を明示して追跡する管理リスト。
425. **リスク登録簿（Risk Register）**: 技術的・業務的・スケジュール上のリスクと発生確率・影響度・回避策を一覧管理するドキュメント。
426. **RAIDログ（Risks, Assumptions, Issues, Dependencies）**: プロジェクトの4大不確実要素を一括追跡し、要件定義から実装まで統制する管理手法。
427. **プレモーテム（Pre-Mortem）**: 「このプロジェクトが失敗した」と仮定して原因を逆算列挙し、要件・設計段階で先回り対策を打つ手法。
428. **ポストモーテム（Post-Mortem）**: 障害や手戻りの原因を非難なき文化（Blameless）で分析し、再発防止ルールをコンテキストへ還元する振り返り。
429. **インセプションデッキ（Inception Deck）**: プロジェクトの目的・エレベーターピッチ・やらないことリスト・トレードオフスライダーを10問で合意する資料群。
430. **トレードオフスライダー（Trade-off Slider）**: 品質・納期・コスト・スコープのどれを最優先しどれを譲歩するかを視覚的に合意するツール。
431. **エレベーターピッチ（Elevator Pitch）**: プロダクトの対象顧客・課題・提供価値・差別化ポイントを数十秒で伝わる定型文に凝縮した要約。
432. **PR/FAQ（Working Backwards）**: リリース時のプレスリリースと想定FAQを最初に書き、顧客視点から要件を逆算定義する手法。
433. **ワンページャー（One-Pager）**: 背景・目的・提案概要・成功指標を1ページに凝縮し、経営層やチームと素早く方向性を合わせる文書。
434. **インパクトマッピング（Impact Mapping）**: 目標（Why）→対象者（Who）→行動変化（How）→施策（What）の4層で要件の根拠を可視化する手法。
435. **オポチュニティソリューションツリー（OST）**: 達成したいアウトカムから顧客機会・解決策・検証実験をツリー状に整理する継続的発見ツール。
436. **ユーザーインタビュー設計**: 誘導質問を避け、過去の具体的行動事実から潜在ニーズと制約を引き出すための質問設計。
437. **ユーザビリティテスト（Usability Testing）**: プロトタイプや試作UIを実際のユーザーに操作してもらい、迷いや誤解を観察して要件へ反映する検証。
438. **ヒューリスティック評価**: ニールセンの10原則など確立されたUI指針に基づき、専門家やAIが画面仕様の問題点を事前点検する手法。
439. **ドッグフーディング（Dogfooding）**: 開発チーム自身が試作品や新機能を日常利用し、実運用視点から要件の不足や摩擦を発見する実践。
440. **コンテキストインタビュー（Contextual Inquiry）**: ユーザーの実際の業務現場・作業環境を観察しながら質問し、暗黙の業務ルールを抽出する調査法。
441. **要件ワークショップ（Requirements Workshop）**: ビジネス・デザイン・開発が集まり、短時間で要件抽出・優先順位付け・合意形成を行う協働セッション。
442. **バックログリファインメント（Backlog Refinement）**: 実装着手前にストーリーを分割・明確化し、受け入れ基準と依存関係を整える継続的メンテナンス。
443. **チケット駆動要件管理**: Issueやチケット単位で要件・設計リンク・受け入れ基準・PRを紐づけ、実装履歴と仕様を直結させる運用。
444. **テンプレート標準化（Document Standardization）**: PRD・Design Doc・ADR・議事録の雛形を統一し、AIの読解精度と作成速度を高める整備。
445. **ドキュメントLint（Doc Linting）**: リンク切れ、見出し構造違反、禁止用語、表記ゆれをCIで自動検出し仕様書品質を維持する仕組み。
446. **スタイルガイド（Documentation Style Guide）**: 敬体/常体、用語表記、図表ルール、ファイル命名規則を統一する執筆基準書。
447. **ドキュメントの鮮度スコア（Doc Freshness Metric）**: 最終更新日と関連コード変更履歴の差分を監視し、陳腐化した仕様書を自動アラートする指標。
448. **ドキュメントのアーカイブ運用**: 廃止された仕様や旧バージョンの設計書を明確に隔離し、AIが現行仕様と混同しないようにする整理手順。
449. **知識ベース統合（Knowledge Base Integration）**: Notion・Confluence・GitHub Wiki・社内資料とリポジトリ内の仕様書を連携・同期する運用設計。
450. **議事録の構造化（Structured Meeting Notes）**: 雑談や発散議論から「決定事項・アクションアイテム・要件変更・未決事項」を即座に抽出する記録形式。
451. **音声・文字起こしからの要件抽出**: ミーティングの文字起こしログをAIで解析し、PRDやチケット案へ変換する要件定義ワークフロー。
452. **視覚的合意形成（Visual Alignment）**: テキストのみの認識ズレを防ぐため、画面モック・フロー図・データ図を必ず添えて確認する習慣。
453. **ディスカッションから仕様への昇格**: SlackやPRコメント上の口頭・チャット合意をそのまま放置せず、正本の仕様書やADRへ転記する運用ルール。
454. **レビューチェックリスト（Spec Review Checklist）**: 非機能要件・異常系・権限・データ移行・AI制約など、仕様レビュー時に必ず確認する標準項目集。
455. **ゲートレビュー（Phase Gate Review）**: 要件確定・設計確定・リリース前など各工程の境界で品質基準の充足を確認する承認関門。
456. **ウォークスルー（Specification Walkthrough）**: 作成者が仕様書を順を追って説明し、参加者全員で解釈の食い違いを洗い出す合同検証手法。
457. **インスペクション（Formal Inspection）**: 明確な役割分担と事前精読に基づき、重要仕様の欠陥を厳格に検出する高密度レビュー手法。
458. **AIによる事前レビュー（AI Pre-Review）**: 人間レビューの前にAIへ仕様書の矛盾・曖昧語・エッジケース漏れを点検させ、レビュー負荷を下げる工程。
459. **人間中心の最終判断（Human Accountability）**: AIが仕様案や設計案を生成しても、ビジネス妥当性・倫理・最終責任は人間が負うガバナンス原則。
460. **変更影響通知（Change Notification）**: 仕様やAPI契約の変更時に、影響を受けるフロント・バック・QA・外部連携先へ自動通知する連携運用。
461. **リリースノート仕様（Release Notes Spec）**: ユーザー視点の変更点・破壊的変更・移行手順を要件段階から意識してまとめる伝達ドキュメント。
462. **オンボーディングガイド（Onboarding Guide）**: 新規参画エンジニアや新規AIセッションが開発環境・設計思想・規約を迷わず理解できる案内書。
463. **ランブック（Runbook）**: 障害対応・データ修復・定期メンテナンスの手順を要件および運用設計と連動して整備する実行マニュアル。
464. **FAQ・トラブルシューティング仕様**: 想定される問い合わせや誤操作パターンを要件段階で洗い出し、ヘルプ設計やUI文言へ反映する資料。
465. **マイクロコピー設計（Microcopy Design）**: ボタンラベル、エラーメッセージ、空状態（Empty State）の文言を仕様として明文化しUX品質を高める設計。
466. **空状態・ローディング・エラー状態仕様**: 正常表示だけでなく、データ0件・読込中・通信失敗時の画面仕様を漏れなく定義するUI要件管理。
467. **レスポンシブ・ブレイクポイント仕様**: モバイル・タブレット・デスクトップ各画面幅でのレイアウト変化と操作性を明示するUI設計仕様。
468. **デザインハンドオフ（Design Handoff）**: デザイナーから開発・AIへFigmaやトークン・状態仕様を曖昧さなく引き渡す連携プロセス。
469. **アクセプタンスデモ（Acceptance Demo）**: スプリントやマイルストーン終了時に動く成果物を関係者へ実演し、要件充足を合意する確認会。
470. **フィードバックループ設計（Feedback Loop）**: ユーザー行動データやサポート問い合わせを次の要件定義・コンテキスト更新へ継続還元する循環仕組み。
471. **仕様のバージョンタグ付け**: 大規模リリースごとに仕様書一式へバージョンタグを付与し、過去仕様の参照と監査を容易にする管理。
472. **多拠点・多職種コミュニケーション設計**: PM・エンジニア・デザイナー・CS間で用語と粒度を通訳し、認識の断絶を防ぐ協働設計。
473. **期待値調整（Expectation Management）**: できること・できないこと・段階的実現のロードマップを早期共有し、ステークホルダーとの乖離を防ぐ活動。
474. **段階的合意（Incremental Sign-off）**: 全仕様完成を待たず、全体方針→コア仕様→詳細仕様の順で小刻みに承認を得て手戻りコストを下げる手法。
475. **仕様のモジュール分割（Modular Specification）**: 1つの巨大な仕様書を避け、機能・ドメイン・非機能ごとにファイル分割して並行編集とAI読込を最適化する構成。
476. **リンク整合性保証（Referential Integrity in Docs）**: 仕様書間の相互リンクや要件ID参照が壊れていないことを自動テストで保証するドキュメント品質管理。
477. **サンプルデータ・フィクスチャ仕様**: 開発・テスト・デモで共通利用する現実的なダミーデータと境界値データの仕様定義。
478. **モックサーバー仕様（Mock Server Spec）**: OpenAPI等の契約から即座にモックAPIを立ち上げ、バックエンド完成前にUI検証と合意を進める手法。
479. **スモークテスト仕様（Smoke Test Spec）**: 最も重要な中核ユースケースが最低限動作することを確認するための最小検証シナリオ定義。
480. **受け入れテスト計画（UAT Plan）**: 業務担当者や発注者が本番相当環境で要件充足を最終検証するための手順・データ・合格基準計画。
481. **移行リハーサル計画（Migration Rehearsal Plan）**: 本番切替前にデータ移行手順・所要時間・切り戻し手順を事前検証するための計画仕様。
482. **教育・トレーニング要件（Training Requirements）**: 新機能導入に伴いエンドユーザーや運用担当者へ必要となるマニュアル・研修内容の定義。
483. **廃止計画（Deprecation & Sunset Plan）**: 旧機能・旧APIのサポート終了予告、移行猶予期間、完全停止手順を事前に規定するライフサイクル仕様。
484. **ライセンス・OSS利用方針**: 導入可能なOSSライセンス種別や禁止ライセンスを事前定義し、AIによる不適切なライブラリ採用を防ぐ制約文書。
485. **外部ベンダー・API選定基準**: 外部SaaSやAPIを採用する際のSLA・料金体系・ロックインリスク・セキュリティ認証の評価基準。
486. **契約・法務レビュー連携**: 利用規約・プライバシーポリシー・特定商取引法表示など法的要件を仕様書と同期させて確認するプロセス。
487. **セキュリティチェックシート**: 認証・暗号化・ログ・脆弱性管理など組織標準のセキュリティ基準を要件定義時に点検する確認表。
488. **データ保持・削除ポリシー文書**: 法令と事業要件に基づき、テーブルやログ種別ごとの保持期間と自動削除ルールを明記した仕様書。
489. **AI利用ガバナンスポリシー**: 開発プロセスでのAI利用範囲、機密データ入力禁止基準、生成物の人間レビュー義務を定めた組織ルール。
490. **コンテキスト資産の棚卸し（Context Inventory）**: プロジェクト内のルール・スキル・仕様書・テンプレートの一覧と利用状況を定期点検する管理活動。
491. **ナレッジ継承設計（Knowledge Transfer）**: 担当者交代やチーム拡大時にも、仕様書とADRとコンテキスト資産だけで即戦力化できる引き継ぎ構造。
492. **メトリクス可視化ダッシュボード要件**: リリース後にKPI・ガードレール指標・エラー率をリアルタイム監視するための画面・集計仕様。
493. **実験記録（Experiment Log）**: 仮説検証やA/Bテスト、プロンプト比較の結果と学びを蓄積し、次の要件判断の根拠とする記録資産。
494. **失敗事例集（Lessons Learned / Anti-Pattern Catalog）**: 過去の要件漏れ・設計失敗・AI誤動作の事例と教訓をまとめ、同じ過ちを防ぐ予防コンテキスト。
495. **成功パターン集（Playbook / Best Practices）**: 再現性の高い要件定義手順、プロンプト設計、アーキテクチャ構成を標準化したチーム実践ガイド。
496. **仕様書からの自動コード・テスト生成パイプライン**: 確定した仕様書・スキーマ・受け入れ基準を起点に、AIエージェントが実装と検証を自動連鎖させる仕組み。
497. **継続的仕様同期（Continuous Spec Sync）**: コード変更PRごとにAIが仕様書やフォルダ構造ドキュメントの更新要否を検知・提案する自動化運用。
498. **トレーサビリティ自動化（Automated Traceability）**: コミット・PR・テスト結果から要件IDを自動収集し、仕様充足率をリアルタイム可視化する仕組み。
499. **要件成熟度モデル（Requirements Maturity Model）**: 組織やチームの仕様品質・コンテキスト整備度・AI協働効率を段階評価し改善指針を得る枠組み。
500. **コンテキスト駆動開発（Context-Driven Development）**: 厳密な要件仕様と構造化されたコンテキスト基盤を中心に据え、人間とAIが最高精度で共創する次世代開発パラダイム。
