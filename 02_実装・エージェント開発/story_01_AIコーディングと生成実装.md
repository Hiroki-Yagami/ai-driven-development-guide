## 第1部：ストーリーで読む「補完から構造化実装へ」

仕様が固まり、「スマート請求管理」の実装フェーズがスタートした。ミサキはエディタを開き、サトウとペアを組みながらAIコーディングの実践パターンを学んでいく。

---

### シーン1：単行補完から「マルチファイル＆構造編集」へ

ミサキがキーボードを叩くと、エディタ上に薄い文字で次のコードが次々と提案される。

**ミサキ**：「カーソル位置に合わせて提案してくれる**インラインコード補完（Inline Code Completion）**だけでも速いですね！関数の途中を書き直しているのに、後ろのコードとも自然に噛み合っています」

**サトウ**：「それはカーソルの前後両方の文脈を読んで中間を埋める**Fill-in-the-Middle（FIM）**が効いているからだよ。最近はさらに進んで、直近の編集履歴から『次はここを直すはず』と先読みしてくれる**Next Edit Prediction（次編集予測）**も使えるようになっている」

**ミサキ**：「でも、新しいAPIを追加するときは型定義・コントローラー・テストの3ファイルを一気に直したいんですよね」

**サトウ**：「そういうときは**マルチファイル編集（Multi-File Editing）**や**コンポーザー型コーディング（Composer-Style Coding）**の出番だね。しかもファイル全体を丸ごと書き直させるのではなく、変更箇所だけを出力する**差分パッチ生成（Diff / Patch Generation）**や、構文木レベルで正確に書き換える**ASTベースコード編集（AST-Aware Editing）**を使うことで、意図しない破壊的変更を防げるんだ」

**ミサキ**：「なるほど！エディタの型情報や診断エラーをAIに渡す**LSP統合（Language Server Protocol Integration）**や、コードの意味で関連ファイルを探す**セマンティックコード検索（Semantic Code Search）**が裏で動いているから、大きなリポジトリでも迷わないんですね」

---

### シーン2：AIに「正しい制約」を与えて実装させる

ミサキは勢いに乗って、自然言語だけで請求計算ロジックを丸ごと生成させてみた。しかし、細かい型ズレや仕様漏れが出てしまった。

**ミサキ**：「うーん、雰囲気を伝えて対話的に作る**バイブコーディング（Vibe Coding）**は、試作品を数分で作る**高速プロトタイピング（Rapid AI Prototyping）**には最高なんですけど、本番の請求計算だとちょっと怖いですね」

**サトウ**：「そこが使い分けのポイントだよ。本番コードでは、まずインターフェースや型を先に定義してコンパイラを検証器にする**型駆動AI実装（Type-Driven AI Implementation）**や、先にテストを書いて全パスするまでAIに実装させる**テストファーストAIコーディング（AI-TDD）**を使うんだ」

**ミサキ**：「なるほど！いきなり全部を書かせるんじゃなく、まず全体のクラス構造や関数スタブだけ作らせる**スケルトン実装（Skeleton-First Coding）**で設計を確認してから、1機能分をUIからDBまで薄く通す**垂直スライス生成（Vertical Slice Generation）**で段階的に進める**インクリメンタル実装（Incremental Implementation）**なら安心ですね」

**サトウ**：「その通り。しかも、いきなり例なしで頼む**Zero-Shot実装**より、うちの既存モジュールの書き方を2〜3件見せる**Few-Shotコード生成**や、リポジトリに置いた規約ファイルを自動で読ませる**ルールファイル駆動実装（Rules / Instructions Files）**を組み合わせると、**コードスタイル模倣（Style Matching）**の精度が劇的に上がるよ」

---

### シーン3：自動フィードバックループとハルシネーション対策

実装が進む中、AIが存在しないライブラリのメソッド名を書いてビルドエラーが出た。

**ミサキ**：「あ、これ存在しないメソッド名です！いわゆる**ハルシネーションAPI検知**が必要になるケースですね」

**サトウ**：「そう。だからこそ人間が目視で全部探すんじゃなくて、AIがコードを書くたびに自動でビルドや型チェックを走らせてエラーをAIへ返す**コンパイルフィードバックループ**と、ESLintやFormatterを即時実行する**Lint/Formatter自動適用**を組んでおくんだ。さらに、難しいアルゴリズムを書くときはコード出力前に設計思考を書かせる**Chain-of-Thoughtコーディング**や、推論に強い**推論特化モデル活用（Reasoning Models for Coding）**へ切り替える**モデルルーティング（Model Routing）**も効くよ」

**ミサキ**：「さっきから同じチャット画面でずっとエラー修正を続けていたら、だんだんAIの提案が的外れになってきた気がします……」

**サトウ**：「それが、失敗した試行錯誤の履歴が溜まって推論品質が落ちる状態だよ。こまめにセッションを切り替える**コンテキスト汚染対策（Context Hygiene）**が重要なんだ。もし誤った既存コードにAIが引きずられる**アンカリングバイアス回避**をしたいときは、新しいセッションで要件から白紙ベースで作り直させると一発で解決することが多いよ」

---

### シーン4：実務品質の仕上げとセキュリティ・保守性

機能のコア部分が動き出したところで、本番投入に向けた仕上げに入る。

**ミサキ**：「定型的なCRUD処理の**ボイラープレート自動排除**のおかげで、予定よりずっと早く進みました！余った時間で何を補強しておくべきですか？」

**サトウ**：「本番品質に引き上げるなら、まず**エラーハンドリング網羅生成**と**境界値・エッジケース補完**だ。それからZodやPydanticを使った**入力バリデーション自動実装**、SQLインジェクションやXSSを防ぐ**セキュリティ指向プロンプティング**、N+1クエリを避ける**パフォーマンス回帰防止実装**もプロンプトに明示しておこう」

**ミサキ**：「テストしやすいように、副作用のある処理から計算ロジックを切り出す**純粋関数抽出（Pure Function Extraction）**や、外部依存を注入する**依存性注入（DI）設計の実装**もAIに提案してもらえますね！」

**サトウ**：「いいね。そして最後はコミット前にAI自身へ差分を点検させる**プロンプト駆動コードレビュー前検証**を通してから、人間がナビゲーターとして最終確認する**人間主導レビューゲート（Human-in-the-Loop Gate）**をくぐらせよう。AI生成コードをブラックボックスにせず、**コード所有権と理解維持**を徹底することがプロのAI駆動開発だよ」

## 第2部：DUO式・高密度復習フレーズ（声に出して覚える5本）

1. **【次世代エディタ補完と構造編集】**
   「**Fill-in-the-Middle（FIM）** や **Next Edit Prediction** で日常の記述を加速しつつ、横断変更は **LSP統合** と **ASTベースコード編集** を備えた **マルチファイル編集** と **差分パッチ生成** で安全に適用する。」
2. **【制約駆動の本番実装】**
   「検証には **バイブコーディング** による **高速プロトタイピング** を使いつつ、本番コードでは **型駆動AI実装**・**テストファーストAIコーディング（AI-TDD）**・**垂直スライス生成** で品質を担保する。」
3. **【文脈と規約の一貫性】**
   「**ルールファイル駆動実装** と **Few-Shotコード生成** で **コードスタイル模倣** の精度を高め、セッション長期化による品質低下は **コンテキスト汚染対策（Context Hygiene）** で防ぐ。」
4. **【自動検証ループと推論最適化】**
   「**ハルシネーションAPI検知** を **コンパイルフィードバックループ** と **Lint/Formatter自動適用** で自動化し、難所では **モデルルーティング** による **推論特化モデル活用** を組み合わせる。」
5. **【本番品質と人間の責任】**
   「**入力バリデーション自動実装** と **セキュリティ指向プロンプティング** で防御を固め、**プロンプト駆動コードレビュー前検証** の後に **人間主導レビューゲート** を通して **コード所有権と理解維持** を守る。」

## 第4部：現場で活かす深掘り解説

### 1. 実務の判断基準：AIコーディング手法の使い分け早見表

| 実装スタイル | 代表的な手法 | 得意な場面 | 苦手な場面・注意点 |
|---|---|---|---|
| **探索・試作型** | バイブコーディング / 高速プロトタイピング / Zero-Shot実装 | 画面イメージの素早い合意形成、使い捨て検証スクリプト、0→1のPoC | 複雑な業務ロジック、長期保守が前提の本番コード、厳密な型整合 |
| **構造・制約駆動型** | 型駆動AI実装 / テストファーストAIコーディング（AI-TDD） / スケルトン実装 | 請求計算・決済・認証などミスが許されない本番機能、チーム開発 | 仕様が全く固まっていない段階（先に型やテストを定義できない） |
| **規約・模倣強化型** | ルールファイル駆動実装 / Few-Shotコード生成 / ASTベースコード編集 | 既存大規模リポジトリへの機能追加、複数ファイル横断の一貫した実装 | ルールファイルが肥大化・陳腐化すると逆にノイズになる |

> **現場の鉄則**：「試作は **バイブコーディング** で数分、本番は **型駆動AI実装＋AI-TDD＋垂直スライス生成** で堅実に」が鉄板です。コンパイラとテストを「AIの出力を自動採点する検証器」として先に置くことで、生成速度と本番品質を両立できます。

---

### 2. よくある失敗パターン（アンチパターン）と回避策

#### 失敗①：本番ロジックをZero-Shotで丸投げし、仕様漏れとスタイル逸脱が起きる
- **起きること**: 既存コードの流儀やエッジケースを伝えずに生成させ、独自命名・エラー握りつぶし・存在しないAPI呼び出しが混入したコードができあがる。
- **回避策**: **ルールファイル駆動実装** でプロジェクト規約を常時読み込ませ、既存の良質な実装を2〜3件示す **Few-Shotコード生成** を行う。さらに **スケルトン実装** で関数シグネチャと型を合意してから中身を埋めさせる。

#### 失敗②：エラー修正を同じチャットで延々と続け、提案の精度が崩壊する
- **起きること**: 過去の失敗コードや誤った仮説がコンテキストに蓄積し、AIが誤った実装に引きずられて堂々巡りになる。
- **回避策**: 2〜3回修正しても噛み合わないときは **コンテキスト汚染対策（Context Hygiene）** としてセッションをリセットする。**アンカリングバイアス回避** のため、壊れたコードは見せずに要件・型・テストだけを渡して白紙から再生成させる。

#### 失敗③：AI生成コードを「動いたからOK」でマージし、ブラックボックス化する
- **起きること**: N+1クエリや入力バリデーション漏れ、セキュリティ欠陥が本番へ混入し、障害時に誰も修正できなくなる。
- **回避策**: **コンパイルフィードバックループ** と **Lint/Formatter自動適用** で機械的ミスを弾いたうえで、**プロンプト駆動コードレビュー前検証** と **人間主導レビューゲート** を必ず通す。自分で説明できないコードはマージしない **コード所有権と理解維持** を徹底する。

---

### 3. 明日から試せる実践レシピ（3ステップ）

1. **まず「型定義＋テスト」だけを先に書いて渡す**: 次の機能実装では、実装コードを書かせる前にインターフェースと主要ケースのユニットテストを先に用意し、「このテストがすべて通るように最小限で実装して」と **AI-TDD** で依頼する。
2. **「お手本ファイル」を2件指定してルールを固定する**: 規約ファイルにエラー処理・バリデーション・命名ルールを簡潔にまとめ、プロンプトでは既存モジュールを `@file` で参照させて **コードスタイル模倣** の精度を上げる。
3. **コミット前にAI自己レビューを1回挟む**: 実装が終わったら「セキュリティ・境界値・パフォーマンス回帰の観点でこの差分を厳しく点検して」と **プロンプト駆動コードレビュー前検証** を回し、最後に人間が差分を確認してからコミットする。

### 4. 理解度チェック・ミニクイズ

**Q1. 本番の請求計算ロジックのように正確性が求められる機能をAIに実装させる際、雰囲気ベースのバイブコーディングよりも有効なアプローチの組み合わせはどれですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：型駆動AI実装（Type-Driven AI Implementation）とテストファーストAIコーディング（AI-TDD）**
先に厳密な型定義と自動テストを用意することで、コンパイラとテストランナーがAIの出力を客観的に検証するガードレールとなり、仕様漏れや型ズレを大幅に防げます。

</details>

**Q2. 同じチャットでエラー修正を何度も繰り返していたら、AIの回答がどんどん的外れになり、誤った実装に固執し始めました。取るべき最も効果的な対策は何ですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：セッションを切り替えるコンテキスト汚染対策（Context Hygiene）とアンカリングバイアス回避**
失敗履歴が溜まると推論品質が劣化します。新しいセッションを立ち上げ、誤った途中コードを渡さず要件・型・テストからクリーンに再生成させる方が早く正確に解決します。

</details>

**Q3. AIが存在しないライブラリのメソッド名を書いてしまう「ハルシネーションAPI」を、人間の目視だけに頼らず早期検知する仕組みは何ですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：コンパイルフィードバックループ（およびLSP統合・Lint/Formatter自動適用）**
AIがコードを生成するたびにビルド・型チェック・LSP診断を自動実行してエラーをAIへ即座にフィードバックすることで、存在しないAPIや型不一致を自律的に検知・修正できます。

</details>
