## 第1部：ストーリーで読む「1体からチーム協調へ」

「スマート請求管理」の次期リリースでは、一括請求エンジン、多段階承認フロー、監査CSV出力、管理画面の刷新を同時に仕上げる必要が出てきた。1体のエージェントに全部任せようとしたミサキだったが、コンテキストが溢れて精度が落ちてしまう。

### シーン1：単一エージェントの限界とオーケストレーション設計

ホワイトボードの前で、ユイがリリース日程を見ながら相談を切り出した。

**ユイ**：「今回の機能群は範囲が広くて、1体のエージェントに順番に頼むと時間が足りなさそうです。複数のエージェントを同時に動かせませんか？」

**サトウ**：「まさに**マルチエージェントシステム（Multi-Agent System: MAS）**の出番だね。まずは親がタスク分解と進捗統合を担い、複数の実行役へ委譲する**オーケストレーター・ワーカーパターン（Orchestrator-Worker）**から考えるのが王道だよ。もし単発の調査や切り出し作業なら、メインから専用文脈へ任せる**サブエージェント委譲（Subagent Delegation）**が手軽だね」

**ミサキ**：「どうやって仕事を分ければいいんでしょう？」

**サトウ**：「大きな要件をモジュールや機能スライスへ分ける**タスク分解・シャーディング（Task Decomposition & Sharding）**を行うんだ。独立した作業を並列に展開して最後に集約する**ファンアウト・ファンイン（Fan-Out / Fan-In）**と、調査→設計→実装→レビューを順に渡す**ステージドパイプライン（Staged Agent Pipeline）**を組み合わせる。複雑な依存関係があるなら、**DAGベースタスクオーケストレーション**をPython等で明示記述する**コード駆動オーケストレーション（Workflow-as-Code）**にすると確実だよ」

**ユイ**：「逆に、もっと自律的に複数のエージェントが共有ボード越しに引き継ぎ合うやり方もあるんですよね？」

**サトウ**：「うん、それが**スウォーム型エージェント（Agent Swarm）**だ。タスクの性質に合わせて、固定パイプラインと柔軟なスウォームを使い分けるのがコツだね」

### シーン2：コンテキスト隔離と「競合しない」並列開発の仕組み

ミサキは3体のワーカーを並列起動しようとして、ふと手が止まった。

**ミサキ**：「ちょっと待ってください！3体が同時に同じファイルを編集したらコンフリクトだらけになりませんか？それに、あるワーカーの調査ログが親に全部流れ込んだらパンクしそうです」

**サトウ**：「いい気づきだね。まず、各ワーカーに独立した会話履歴を持たせる**コンテキスト隔離（Context Isolation）**が基本だ。逆に親の設計議論を引き継いで複数案を試したいときだけ**コンテキストフォーク（Context Forking）**を使う。そして新規ワーカーは親の会話を知らない前提で、責務と完了条件を自己完結して書く**プロンプト・ブリーフ設計（Clear Worker Briefs）**と、引き継ぎ情報を構造化する**ハンドオフプロトコル（Agent Handoff Protocol）**が命になるよ」

**ミサキ**：「編集の衝突はどう防ぐんですか？」

**サトウ**：「3段構えで防ぐんだ。1つ目は各ワーカーに別々のgit worktreeを渡す**独立ワークスペース共有（Shared Repository Worktree）**。2つ目は編集可能なディレクトリを事前に排他分割する**ファイル所有権パーティショニング（File Ownership Partitioning）**。3つ目は、並列実装を始める前にAPI型定義やスキーマだけ先に固める**インターフェース契約先行協調（Contract-First Parallelism）**だよ」

**ユイ**：「全員が同じ仕様を見られるように、設計書をファイルにまとめておくのも大事ですね」

**サトウ**：「その通り！単一情報源となる**共有仕様アーティファクト（Shared Spec Artifacts）**や、途中で決まった方針を残す**決定ログ共有（Shared Decision Log / ADR）**、全員が非同期に参照できる**共有ブラックボードアーキテクチャ（Shared Blackboard）**を置くんだ。しかも親はポーリングで待たず、完了通知で自動起動する**リアクティブウェイクアップ（Reactive Wakeup）**で動くから無駄がないよ」

### シーン3：役割特化エージェントと多角的な相互検証

並列実装が走り出した。ミサキは各エージェントの役割とモデル割り当てを確認している。

**ミサキ**：「全員に同じ万能プロンプトを渡すより、責務を絞った**役割特化エージェント設計（Role-Specialized Agents）**にした方が精度が高いんですね！」

**サトウ**：「そう。書き込み権限を持たず調査要約に徹する**リサーチ専用サブエージェント（Read-Only Researcher）**、境界値テストを専門に書く**テスト専門エージェント（Dedicated Test Engineer Agent）**、脆弱性や権限漏れを点検する**セキュリティ監査エージェント（Security Auditor Agent）**みたいに専門化するんだ。モデルも全部最高性能にするのではなく、設計やレビューには高推論モデル、定型変換には高速軽量モデルを配る**モデル多様性配置（Heterogeneous Model Fleet）**でコストと速度を最適化するよ」

**ユイ**：「実装したエージェント本人にレビューさせると、自分の思い込みを見逃しませんか？」

**サトウ**：「まさにそこがポイント。作る側と厳しく批評する側を分ける**ジェネレーター・クリティックパターン（Generator-Critic）**や、実装に関わっていない別エージェントが独立検証する**クロスチェック検証（Cross-Verification Agent）**を入れるんだ。設計の難所では複数案を主張・反論させる**ディベート型合意形成（Multi-Agent Debate）**、セキュリティの要所では攻撃者視点で破壊テストを仕掛ける**レッドチーム・ブルーチーム協調（Adversarial Agents）**も強力だよ」

**ミサキ**：「PRレビューでも、設計・セキュリティ・性能・テストの視点で一斉に見てもらう**並列コードレビュー多角化**を使えば、見落としが激減しますね！」

### シーン4：統合ゲート・障害隔離と人間による全体指揮

夕方、各ワーカーの実装ブランチが続々と完了通知を返してきた。しかし、そのうち1体だけ外部モックのエラーで停滞している。

**ミサキ**：「あ、CSV出力担当のワーカーが止まっています！でも他の2つの成果物までやり直しにならずに済むんですよね？」

**サトウ**：「うん、1つの失敗が全体を巻き込まない**部分失敗の隔離（Fault Isolation）**が効いているよ。停滞は**監視・ストール検知エージェント（Swarm Monitor / Watchdog）**が拾ってくれて、ワーカーが自力で解けない仕様矛盾はリードから人間へ段階的に上がる**エスカレーションチェーン（Escalation Chain）**に乗るんだ」

**ユイ**：「無事に揃ったブランチはどう統合するんですか？」

**サトウ**：「**ブランチ隔離マージ戦略（Parallel Branch Merge）**に沿って統合する。行ベースで競合が出ても双方の意図を読んで解消する**セマンティックマージ支援（AI-Assisted Semantic Merge）**が使えるし、最後は統合ブランチ全体でビルドと結合テストを必ず通す**インテグレーションゲート（Integration Verification Gate）**をくぐらせるんだ」

**ミサキ**：「運用面のコストや監視も気になります」

**サトウ**：「全体の上限を握る**トークン・コスト配分制御（Fleet Budget Governance）**と、親から孫・ツール呼び出しまで1本のIDで追える**分散トレース統合（Distributed Agent Tracing）**を入れておけばブラックボックスにならない。人間は全ステップを止めず俯瞰監視して異常時だけ介入する**ヒューマン・オン・ザ・ループ監視（Human-on-the-Loop）**で指揮し、完了後は一時ブランチやworktreeを自動破棄する**クリーンアップ自動化（Ephemeral Resource Teardown）**まで回して完了だよ」

## 第4部：現場で活かす深掘り解説

### 1. 実務の判断基準：単一 vs マルチエージェント構成の使い分け早見表

| 構成パターン | 仕組み | 得意な場面 | 苦手な場面・注意点 |
|---|---|---|---|
| **単一エージェント** | 1つの文脈で調査〜実装〜検証を一貫実行 | 密結合な単一機能の実装、小〜中規模のバグ修正 | タスクが広範囲になるとコンテキストが肥大化し精度が低下する |
| **サブエージェント委譲** | 調査やテストなど単発の重い処理だけ別文脈へ切り出す | 大規模コードベースの調査、ドキュメント要約、独立モジュールの作成 | 細かすぎるタスクを委譲すると通信・起動オーバーヘッドが上回る |
| **オーケストレーター・ワーカー** | 親がタスク分解・統合を担い、複数ワーカーへ並列委譲 | 独立した複数機能の同時実装、ファンアウト・ファンイン型の一括処理 | ブリーフ設計が曖昧だと各ワーカーの成果物が噛み合わない |
| **ステージドパイプライン / スウォーム** | 工程順に引き継ぐ、または共有ボード越しに自律協調 | 調査→設計→実装→監査の定型フロー、探索的な大規模改修 | トークン予算管理とストール監視がないとコスト・遅延が膨らむ |

> **現場の鉄則**：最初から複雑なマルチエージェントを組む必要はありません。**「単一で解けるなら単一、文脈が溢れる調査はサブエージェント委譲、独立スライスが3つ以上あるならオーケストレーター・ワーカー」** と段階的に拡張するのが最も失敗しない選び方です。

### 2. よくある失敗パターン（アンチパターン）と回避策

#### 失敗①：所有権や契約を決めずに並列実装させ、マージ競合地獄になる
- **起きること**: 複数ワーカーが同じ共有ファイルやAPI型定義をバラバラに書き換え、統合時に大量のコンフリクトと仕様不整合が発生する。
- **回避策**: 並列着手前に **インターフェース契約先行協調** で型定義・スキーマを確定し、各ワーカーの編集範囲を排他分割する **ファイル所有権パーティショニング** と **独立ワークスペース共有（git worktree）** を徹底する。

#### 失敗②：親の会話履歴を前提にした雑な指示でワーカーが誤解釈する
- **起きること**: 「さっきの仕様でCSV出力を作って」のような省略指示を出し、コンテキスト隔離された新規ワーカーが別仕様のコードを量産する。
- **回避策**: 新規ワーカーは親の会話を知らない前提で、目的・対象ファイル・制約・完了条件を自己完結させた **プロンプト・ブリーフ設計** を行う。共通仕様は **共有仕様アーティファクト** と **決定ログ共有（ADR）** に置いて全員から参照させる。

#### 失敗③：実装したエージェント自身にレビューさせ、思い込みを見逃す
- **起きること**: 自分で書いたコードの前提ミスやセキュリティ漏れを同じ文脈のまま「問題なし」と自己承認してしまう。
- **回避策**: 実装役と批評役を分離する **ジェネレーター・クリティックパターン** や **クロスチェック検証** を導入し、PR段階では設計・セキュリティ・テストの専門視点で **並列コードレビュー多角化** を行う。

### 3. 明日から試せる実践レシピ（3ステップ）

1. **まずは「リサーチ専用サブエージェント」から始める**: 本格的な並列実装の前に、書き込み権限を持たない調査専用サブエージェントへ既存コードの調査・要約を委譲し、メインのコンテキストを清潔に保つ効果を体験する。
2. **並列実装前に「契約ファイル＋所有権表」を1枚書く**: 2体以上のワーカーを動かすときは、先に型定義ファイルをコミットし、「ワーカーAは `src/billing/`、ワーカーBは `src/export/` のみ編集可」と **ファイル所有権パーティショニング** を明文化する。
3. **統合時は必ず「インテグレーションゲート」を通す**: 各ワーカーのブランチをマージした後、統合ブランチ全体で型チェック・結合テスト・Lintを一括実行し、全合格を確認してから **クリーンアップ自動化** で一時worktreeを片付ける。

### 4. 理解度チェック・ミニクイズ

**Q1. 複数のワーカーエージェントに別々の機能を並列実装させる際、ファイル編集の衝突やインターフェースの食い違いを事前に防ぐための3つの仕組みは何ですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：独立ワークスペース共有（git worktree）、ファイル所有権パーティショニング、インターフェース契約先行協調**
作業ディレクトリを分離し、編集対象ディレクトリを排他分割し、共通の型・API契約を先に固めておくことで、並列作業後のマージ破綻を防げます。

</details>

**Q2. 親エージェントから新規ワーカーを起動したとき、ワーカーが親の過去の会話履歴を持っていない前提で、責務・参照先・完了条件を自己完結して記述する設計を何と言いますか？**
<details>
<summary>解答と解説を見る</summary>

**答え：プロンプト・ブリーフ設計（Clear Worker Briefs）**
コンテキスト隔離によりワーカーは白紙状態から始まるため、省略や暗黙知を排した明確なブリーフと共有仕様アーティファクトの参照指定が品質を左右します。

</details>

**Q3. 実装を担当したエージェント自身の思い込みによる見落としを防ぐため、作成側とは独立したエージェントに厳しい検証・指摘を行わせる協調パターンは何ですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：ジェネレーター・クリティックパターン（Generator-Critic）（またはクロスチェック検証）**
生成と批評の役割・文脈を分離することで、自己正当化バイアスを排除し、バグやセキュリティ欠陥の検出力を高められます。

</details>
