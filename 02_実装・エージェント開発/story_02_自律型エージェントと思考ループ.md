## 第1部：ストーリーで読む「補完AIから自律型エージェントへ」

「スマート請求管理」の初期機能が動き始め、バックログには細かな機能追加や修正Issueが積み上がってきた。ユイの提案で、チームはコード補完だけでなく、タスク単位を自律的に進めるエージェント運用へ踏み出すことにした。

### シーン1：思考ループの仕組みと「いきなり書かない」探索規律

ミサキは新しい請求ステータス追加のIssueをエージェントに渡し、画面上で思考ログが流れるのを眺めている。

**ミサキ**：「すごいですね！単なるコード補完じゃなくて、自分でファイルを検索して編集してテストまで回す**自律型コーディングエージェント（Autonomous Coding Agent）**だと、開発の景色が一変します。これって裏側でどう考えているんですか？」

**サトウ**：「基本になるのが、思考（Thought）・行動（Action）・観測（Observation）を交互に回す**ReActパターン（Reason + Act）**だよ。ただ、大きなタスクを成り行きで進めると迷子になりやすいから、最初に全体手順を組み立ててから実行し、必要に応じて再計画する**Plan-and-Executeアーキテクチャ**や、実行フェーズをノードと条件分岐で明示管理する**エージェント状態遷移グラフ（Agent State Graph）**を組み合わせるんだ」

**ユイ**：「失敗したときはそのまま諦めちゃうんですか？」

**サトウ**：「いや、失敗したエラーを言語で振り返って次の試行に活かす**Reflexion（自己省察ループ）**や、複数の設計案を木構造で分岐評価する**Tree of Thoughts（ToT）**を使えば粘り強く解決できる。ただし、いきなりファイルを編集させると事故るから、最初は検索と閲覧だけに徹する**読み取り専用探索フェーズ（Read-Only Discovery）**で呼び出し元を洗い出す**変更影響範囲分析（Blast Radius Analysis）**を行わせるんだ」

**ミサキ**：「なるほど！進捗を見失わないように**作業チェックリスト管理（Task / Step Tracking）**を更新させつつ、実装前に計画書を出してもらって人間がOKを出す**対話的計画承認フロー（Plan-First Approval）**を挟めば、ユイさんも安心ですね！」

### シーン2：ツール連携・MCP・メモリとコンテキスト制御

探索が終わったエージェントは、複数のソースファイルを同時に読み込み、データベースの定義まで参照し始めた。

**ミサキ**：「わっ、エディタ内の検索だけじゃなくて、テストコマンドまで自分で叩いています！」

**サトウ**：「LLMがJSONスキーマに従って外部機能を呼ぶ**ツール呼び出し（Tool Calling / Function Calling）**と、ビルドやGitを直接叩ける**ターミナル自律操作（Shell Execution Tool）**のおかげだね。独立したファイル読み込みを1ターンで同時に投げる**並列ツール実行（Parallel Tool Execution）**を使うと、待ち時間もぐっと減るよ」

**ユイ**：「社内の仕様書DBや監視ツールにも繋げるんですか？」

**サトウ**：「そこで効くのが、外部データソースやツールを標準プロトコルで接続できる**Model Context Protocol（MCP）**だよ。しかも人間向けCLIをそのまま渡すのではなく、AIが誤操作しにくいよう専用設計した**Agent-Computer Interface（ACI）**を整えてあげると精度が段違いに上がる」

**ミサキ**：「でも、コマンドの出力やファイルの中身が増えると、すぐコンテキストがいっぱいになりませんか？」

**サトウ**：「そこを統合設計するのが**コンテキストエンジニアリング（Context Engineering）**だ。今の作業状態を保つ**短期ワーキングメモリ（Working Memory）**と、セッションを跨いでプロジェクトの知見を蓄える**長期メモリ（Long-Term Memory）**を使い分ける。さらに、膨大なログのエラー行だけ切り出す**出力トランケーション制御（Output Truncation）**、古い履歴を自動要約する**コンテキストコンパクション（Context Compaction）**、大きな手順書は目次だけ渡して必要な章だけ読ませる**段階的開示（Progressive Disclosure）**を組み合わせるんだ」

### シーン3：暴走防止・自己修復ループとセキュリティの境界線

実装フェーズに入ったエージェントは、型エラーとテスト失敗を検知すると、自動で原因を修正して再テストを始めた。

**ミサキ**：「おお、テストが通るまで自動で直していく**自己修復ループ（Self-Healing Loop）**ですね！……あ、でも同じエラーで3回連続つまずいています。このまま放置するとAPI代がすごいことになりそう」

**サトウ**：「だからこそ安全装置が必須なんだ。最大ターン数や費用を制限する**ステップ予算・ループ上限（Step Budget / Max Iterations）**と、同じ編集の往復を止める**無限ループ検知（Loop Detection）**を入れておく。行き詰まったら、各ステップで保存しておいた**チェックポイント・スナップショット機構**まで巻き戻して別案を試す**バックトラッキング（Backtracking）**に切り替えるんだよ」

**ユイ**：「セキュリティ面も気になります。エージェントがうっかり本番DBを消したり、外部の悪意あるIssue本文に騙されたりしませんか？」

**サトウ**：「そこは多層防御で守るよ。まずコマンド実行はホストから隔離された**サンドボックス実行環境（Sandboxed Execution）**に閉じ込め、タスクに不要な権限を渡さない**最小権限の原則（Least Privilege for Agents）**を徹底する。破壊的操作の前には人間へ確認を求める**権限昇格・承認ゲート（Approval Gate）**を置き、プロンプト任せにせずルールエンジンで危険コマンドを強制遮断する**決定論的ガードレール（Deterministic Guardrails）**も組むんだ」

**ミサキ**：「外部ドキュメントに仕込まれた命令を弾く**プロンプトインジェクション防御（Agent Security）**と、ログにAPIキーが出ても自動で伏せる**シークレットマスキング（Secret Redaction）**まで揃っていれば、安心して任せられますね」

### シーン4：検証ファーストの完了規範と人間の責任境界

数分後、エージェントからタスク完了の通知が届いた。画面には変更ファイル一覧とテスト実行ログが添えられている。

**ミサキ**：「今回は仕様に迷う箇所があったみたいで、途中で勝手に推測せず確認を投げてくれました。これが**曖昧性解消・質問エスカレーション**ですね」

**サトウ**：「そう。そして完了判定には『全ユニットテスト合格・ビルド成功・Lintエラーゼロ』といった明確な**停止条件設計（Stopping Criteria）**を定義しておく。コードを書いただけで『終わりました』と言わせず、必ず実コマンドを叩いて結果を確認させる**検証ファースト完了規範（Verification Before Completion）**と、テスト件数や変更根拠を添える**実行結果の証拠ベース報告（Evidence-Based Reporting）**を徹底するんだ」

**ユイ**：「なるほど！しかも余計なフォーマット変更をせず、最小限の差分に抑える**差分最小化原則（Minimal Diff Principle）**を守ってくれているから、レビューもしやすいですね」

**サトウ**：「慣れてきたら、僕らが別の作業をしている裏で専用ブランチやgit worktreeに隔離して進める**ワークスペース隔離（Git Worktree / Branch Isolation）**と**バックグラウンドエージェント（Background / Async Agent）**も活用できる。すべての判断とツール履歴は**監査ログ・実行トレース（Agent Audit Trail）**に残るけれど、アーキテクチャ変更や本番適用をどこまでAIに任せ、どこから人間が責任を持つかという**人間とエージェントの責任境界設計**をチームで握っておくことが一番大切だよ」

## 第4部：現場で活かす深掘り解説

### 1. 実務の判断基準：エージェント思考ループの使い分け早見表

| 思考・実行パターン | 特徴 | 得意な場面 | 苦手な場面・注意点 |
|---|---|---|---|
| **ReActパターン** | 思考→行動→観測を逐次繰り返す基本ループ | 小〜中規模の調査、局所的なバグ修正、シンプルなコマンド実行 | ステップ数が増えると全体方針を見失いやすく、迷走リスクがある |
| **Plan-and-Execute** | 最初に全体計画を立ててから順次実行・再計画 | 複数ファイルに跨る機能追加、仕様書に基づく段階的実装 | 探索不足のまま計画を立てると前提が崩れ、手戻りが大きくなる |
| **Reflexion / Tree of Thoughts（ToT）** | 失敗の言語的省察や複数案の分岐評価を行う | 難解な原因究明、複数アーキテクチャ案の比較検討 | トークン消費とレイテンシが増えるため、定型作業には過剰 |
| **エージェント状態遷移グラフ** | 調査→計画→実装→検証を明示的な状態遷移で制御 | 企業の本番ワークフロー、再現性と監査性が求められる業務 | 設計コストがかかるため、一回限りのアドホック作業には不向き |

> **現場の鉄則**：いきなり編集させず、**「読み取り専用探索フェーズ → 対話的計画承認フロー → 自己修復ループ → 検証ファースト完了規範」** の4段構えを標準型にすると、自律性と安全性を高い次元で両立できます。

---

### 2. よくある失敗パターン（アンチパターン）と回避策

#### 失敗①：事前探索なしで編集を開始させ、影響範囲を見落として壊す
- **起きること**: エージェントが1ファイルだけを見て修正し、呼び出し元の型や他モジュールの前提を破壊する。
- **回避策**: 着手時は必ず **読み取り専用探索フェーズ** で関連コードと依存関係を洗い出させ、**変更影響範囲分析（Blast Radius Analysis）** の結果を計画書に書かせてから **対話的計画承認フロー** を通す。

#### 失敗②：ループ上限やガードレールを設定せず、暴走・高額課金・危険操作を招く
- **起きること**: 同じエラーを延々と修正し続けてAPI予算を浪費したり、意図しない削除コマンドや外部送信を実行してしまう。
- **回避策**: **ステップ予算・ループ上限** と **無限ループ検知** を必ず設定し、コマンド実行は **サンドボックス実行環境** と **最小権限の原則** の下に置く。危険操作はプロンプト任せにせず **決定論的ガードレール** と **権限昇格・承認ゲート** で強制遮断する。

#### 失敗③：エージェントの「完了しました」という自己申告をそのまま信じる
- **起きること**: 実際にはテストを実行していなかったり、ビルドエラーやLint警告が残ったまま完了報告が上がってくる。
- **回避策**: 「全テスト合格・ビルド成功・差分最小化」などの **停止条件設計** を明示し、必ず実コマンドの出力を根拠として提示させる **検証ファースト完了規範** と **実行結果の証拠ベース報告** を義務付ける。

### 3. 明日から試せる実践レシピ（3ステップ）

1. **プロンプトに「まず調査と計画だけ」を定型文で入れる**: エージェントへタスクを渡す際、「最初はファイル編集禁止。関連箇所の調査と影響範囲、チェックリストを提示し、承認後に実装へ進むこと」と指定する。
2. **「3回失敗したら止まって報告」の予算ルールを置く**: 無限ループを防ぐため、「同じエラーで3回連続失敗したらチェックポイントへ戻し、原因仮説と選択肢を人間へエスカレーションすること」と明記する。
3. **完了報告に「実行コマンドと結果」を必須化する**: 作業の締めくくりに、実行したテストコマンド・成功件数・変更ファイル一覧を添える **実行結果の証拠ベース報告** をルール化し、レビュー時間を短縮する。

### 4. 理解度チェック・ミニクイズ

**Q1. エージェントに既存機能の変更を任せる際、いきなりファイルを書き換えさせず、先に依存関係や呼び出し元を安全に把握させるための初期フェーズは何ですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：読み取り専用探索フェーズ（Read-Only Discovery）と変更影響範囲分析（Blast Radius Analysis）**
書き込みツールを使わず検索・閲覧だけに限定して影響範囲を洗い出すことで、見落としによる破壊的変更を未然に防げます。

</details>

**Q2. 破壊的なシェルコマンドの実行や機密情報の漏洩を防ぐ際、プロンプトの注意書きだけに頼らず、ルールエンジンやOS隔離で確実に遮断する考え方を何と言いますか？**
<details>
<summary>解答と解説を見る</summary>

**答え：決定論的ガードレール（Deterministic Guardrails）（およびサンドボックス実行環境・最小権限の原則）**
LLMの確率的な判断に安全性を委ねず、ツール実行層で機械的・決定論的に危険コマンドをブロックし、必要に応じて承認ゲートを挟むことが実務の基本です。

</details>

**Q3. エージェントがコードを書き終えただけで「完了」と主張するのを防ぎ、必ずテストやビルドを実行した実測結果をもとに報告させる規範は何ですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：検証ファースト完了規範（Verification Before Completion）と実行結果の証拠ベース報告（Evidence-Based Reporting）**
明確な停止条件を満たしたことをコマンド実行ログという証拠で裏付けることで、ハルシネーションによる虚偽の完了報告を防ぎます。

</details>
