## 第1部：ストーリーで読む「『なんとなく良さそう』を卒業するAI品質評価」

「スマート請求管理」に、経理規定を参照して問い合わせに答えるRAGチャットと、請求データの照合を行うAIエージェントが追加されることになった。しかし従来の単体テストだけでは、確率的に揺れるAIの品質を保証できない。ユイ、ミサキ、サトウの3人は体系的なEvals（評価基盤）の構築に乗り出す。

### シーン1：「なんとなく良さそう」を卒業するLLM評価と評価駆動開発

ミサキがプロンプトを少し書き換え、3件ほど手動で質問を投げて「いい感じに答えてくれました！」と報告した。

**サトウ**：「ミサキさん、その3件が通っても、別の50件が壊れているかもしれないよ。生成AIアプリでは、従来の単体テストに相当する **LLM評価 (LLM Evals)** が品質の土台になる。プロンプトをいじる前に評価データと合格基準を先に決める **評価駆動開発 (Eval-Driven Development / EDD)** で進めよう」

**ユイ**：「リリース前に確認するテストと、本番に出した後の確認は分けた方がいいですよね？」

**サトウ**：「その通り。デプロイ前に固定データで比較する **オフライン評価 (Offline Evaluation)** と、本番で実ユーザーの行動や業務KPIを追う **オンライン評価 (Online Evaluation)** の両輪が必要だよ。まずは経理の専門家が監修した正解集である **ゴールデンデータセット (Golden Evaluation Dataset)** を作ろう。希少なケースはLLMで補う **合成評価データ生成 (Synthetic Eval Data Generation)** で広げるんだ」

**ミサキ**：「採点基準はどう設計すればブレなくなりますか？」

**サトウ**：「正確性や安全性などの軸を明文化する **評価ルーブリック設計 (Evaluation Rubric Design)** が要だよ。しかも実務では曖昧な5段階採点より『要件を満たしたか』を二値で切る **バイナリ合否評価 (Binary Pass/Fail Eval)** の方が改善アクションが明確になる。まずはJSON構文や数値一致をコードで厳密判定する **決定的グレーダー (Deterministic Grader)** を一次関門にし、そこを通った出力だけをLLM採点や人間確認へ回す **ハイブリッド評価パイプライン (Hybrid Evaluation Pipeline)** を組もう」

### シーン2：LLM-as-a-Judgeの罠とRAG・エージェント評価の勘所

ミサキがさっそくLLMに採点させる仕組みを動かしてみたが、思わぬ偏りに気づく。

**ミサキ**：「サトウさん、高性能なLLMを審査員にする **LLM-as-a-Judge** を組んだんですけど、なぜか文章がダラダラ長い回答ばかり高得点になります……」

**サトウ**：「よく気づいたね！それは典型的な審査員バイアスなんだ。絶対点数より2つの出力を並べて優劣を比べる **ペアワイズ比較評価 (Pairwise Comparison Eval)** の方が精度が出やすいんだけど、そこにも罠がある。選択肢の順番で偏る傾向は提示順を入れ替えて両方向評価する **ポジションバイアス対策 (Position Bias Mitigation)** で防ぎ、長文びいきは簡潔性ペナルティを入れる **冗長性バイアス対策 (Verbosity Bias Mitigation)** で抑えるんだ。そして定期的に人間の専門家採点と一致度を測る **人間評価との整合性検証 (Human-Judge Alignment)** で審査員を校正しよう」

**ユイ**：「経理規定を調べるRAGチャットでは、規定に書いていないことを勝手に捏造されるのが一番怖いです」

**サトウ**：「RAGの品質は **RAG評価トライアド (RAG Evaluation Triad)** で分解して測るんだ。特に、回答の主張が参照文書に裏付けられているかを見る **忠実度評価 (Faithfulness / Groundedness Eval)**、正解に必要な文書を漏れなく検索できたかを測る **コンテキスト再現率 (Context Recall)**、そして事実誤認の割合を追う **ハルシネーション率測定 (Hallucination Rate Measurement)** は必須だね」

**ミサキ**：「請求照合をするAIエージェントの方は、最終結果だけ見れば十分ですか？」

**サトウ**：「いや、偶然当たっただけだと本番で壊れるよ。思考手順やステップ効率まで追う **エージェント軌跡評価 (Agent Trajectory Evaluation)** と、正しいツールをスキーマ通りの引数で呼べたかを測る **ツール呼び出し精度 (Tool Calling Accuracy)** までセットで見よう」

### シーン3：本番運用を見据えたPass^k・安全性・コストと速度の検証

評価結果が揃い始めると、ユイから「本番のお客さまに届ける現実的なライン」についての質問が出た。

**ユイ**：「評価スコアが90%を超えたモデル候補が2つあるんですが、どちらを本番に採用すべきか迷っています」

**サトウ**：「まず注意したいのが安定性の指標だよ。k回試して1回でも当たればOKの **Pass@k 指標 (Pass@k Metric)** ではなく、k回すべて安定して成功する確率を見る **Pass^k 指標 (Pass^k Consistency Metric)** で比較しよう。本番業務で『たまに失敗する』は致命的だからね。それに公開ベンチマークのスコアを鵜呑みにせず、自社固有の請求業務で作った **プライベートベンチマーク構築 (Private Domain Benchmark)** で判断するのが鉄則だよ」

**ミサキ**：「プロンプトを直したり、安い新モデルへ切り替えたりするたびに全件チェックするのも大事ですね」

**サトウ**：「そう。修正による劣化を防ぐ **プロンプト回帰テスト (Prompt Regression Testing)** と、モデル切替時の互換性を測る **モデル移行比較評価 (Model Migration Evaluation)** を回そう。API連携が壊れないように **構造化出力準拠率 (Structured Output Compliance Rate)** を確認しつつ、攻撃者視点でプロンプトインジェクションや権限逸脱を仕掛ける **レッドチーミング評価 (AI Red Teaming)** で弱点も炙り出すんだ」

**ユイ**：「コストと応答スピードのバランスも気になります。精度が1%高くても応答に15秒かかったら使われなくなってしまいます」

**サトウ**：「まさにそこ！初回トークン到達時間や全体応答時間を測る **レイテンシ評価指標 (TTFT / TPOT / E2E Latency)** と、課金コスト対スコアを可視化する **コスト対品質パレート分析 (Cost-Quality Pareto Analysis)** を並べて、ビジネス要件に最も合う構成を選ぼう」

### シーン4：エラー分析と評価データフライホイールで精度を育て続ける

評価パイプラインが回り始めた後、サトウは最も重要な「改善の回し方」を2人に伝えた。

**ミサキ**：「スコアが82%からなかなか伸びません。プロンプトをいろいろ書き換えているんですが、手探り状態です……」

**サトウ**：「数字だけ眺めてプロンプトを弄るのは遠回りだよ。Evalsで一番大事なのは、失敗ケースを人間が直接読み込んで根本原因を分類する **エラー分析ワークフロー (Systematic Error Analysis)** なんだ。検索漏れ・ツール引数誤り・形式崩れといった類型を整理する **失敗モード分類体系 (Failure Mode Taxonomy)** を作り、全体平均だけでなくカテゴリ別や難易度別に分解する **スライスベース評価 (Slice-Based Evaluation)** を見ると、どこを直せば一気に効くかが一目で分かるよ」

**ユイ**：「改善版のスコアが2%上がったとき、それが『たまたまの誤差』じゃないかも確認したいですね」

**サトウ**：「そこで **統計的有意性検定 (Statistical Significance Testing in Evals)** を入れて、偶然のばらつきと本物の改善を見分けよう。さらにPRごとに軽量評価を回す **CI組み込みEvals (Eval-Driven CI/CD)** を整備し、PR時の高速スモーク・日次フル回帰・リリース前レッドチームと階層化する **段階的評価ティア (Tiered Evaluation Strategy)** で速度と網羅性を両立するんだ」

**ユイ**：「リリース可否の判断基準もチームで揃えておきたいです！」

**サトウ**：「精度・安全性・レイテンシ・コストの全閾値をまとめた **スコアカード・リリース基準 (AI Release Readiness Scorecard)** を合意しよう。そしてリリース後は、再生成クリックや離脱などの行動から品質を推定する **暗黙的フィードバック評価 (Implicit User Feedback Metrics)** を拾い、本番の失敗事例を再び評価セットへ還流させる **評価データフライホイール (Evaluation Data Flywheel)** を回し続ければ、AI品質は使うほど強くなっていくよ」

## 第4部：現場で活かす深掘り解説

### 1. 実務の判断基準：評価グレーダーと評価ティアの使い分けマトリクス

| 評価手法・グレーダー | 実行コスト・速度 | 得意な検証対象 | 弱点・運用時の注意点 |
|---|---|---|---|
| **決定的グレーダー（コード判定）** | 超高速・ほぼ無料 | JSONスキーマ準拠、ツール名・引数型、禁止語チェック、計算結果一致 | 自由記述のニュアンスや文章の自然さは測れない |
| **LLM-as-a-Judge（モデル採点）** | 中速・中コスト | 忠実度（RAG根拠整合）、要約の網羅性、トーン、ペアワイズ比較 | ポジションバイアス・冗長性バイアスがあるため **人間評価との整合性検証** が必須 |
| **人間の専門家レビュー** | 低速・高コスト | ゴールデンデータセット作成、エラー分析、審査員モデルの校正、高リスク判断 | 全PRで回すのは不可能。定期サンプリングと基準策定に集中させる |
| **段階的評価ティア（CI統合）** | PR: 高速 / 日次: 網羅 / リリース前: 厳格 | プロンプト回帰検知（PR）、フル回帰（日次）、レッドチーミング（リリース前） | 全件を毎PRで回すとCIが詰まるため、階層化とスコアカード基準の合意が鍵 |

> **現場の鉄則**：**「まず決定的グレーダーで機械的に弾き、通ったものだけをバイナリ合否評価のLLM-as-a-Judgeへ流す」ハイブリッド評価パイプライン** が最も高コスパです。そしてスコア改善の最短ルートはプロンプトの手探り修正ではなく、失敗ログを人間が直接読む **エラー分析ワークフロー** です。

### 2. よくある失敗パターン（アンチパターン）と回避策

#### 失敗①：公開ベンチマークの順位や「手元で3件試した感覚」でモデルを決める
- **起きること**: 汎用ベンチマークで1位のモデルを採用したのに、自社固有の経理用語・出力形式・ツール呼び出しで頻繁に失敗し、レイテンシやコストも要件を超過する。
- **回避策**: 自社業務の実データから **ゴールデンデータセット** と **プライベートベンチマーク構築** を行い、**Pass^k 指標**・**レイテンシ評価指標**・**コスト対品質パレート分析** を並べて客観的に選定する。

#### 失敗②：LLM-as-a-Judgeのスコアを無検証で信じ込む
- **起きること**: 審査員LLMが「長い回答ほど高評価」「最初に提示された回答を好む」といったバイアスを持ち、冗長で根拠の薄い回答へ最適化されてしまう。
- **回避策**: 曖昧な5段階採点をやめて **評価ルーブリック設計** に基づく **バイナリ合否評価** を採用し、**ポジションバイアス対策**（順序入替）と **冗長性バイアス対策** を組み込む。さらに定期的に **人間評価との整合性検証** で一致率を測る。

#### 失敗③：全体平均スコアだけを見て、特定ドメインの致命的な劣化を見逃す
- **起きること**: 全体スコアは85%→87%に上がったように見えるのに、実は「請求金額の例外処理」スライスだけ50%に急落していたまま本番リリースしてしまう。
- **回避策**: 失敗を類型化する **失敗モード分類体系** と、カテゴリ・難易度別の **スライスベース評価** を標準化し、改善幅が偶然でないかを **統計的有意性検定** で確かめたうえで **スコアカード・リリース基準** により昇格判定する。

### 3. 明日から試せる実践レシピ（3ステップ）

1. **まずは20〜30件の「小さなゴールデンデータセット」を作る**: 実際の問い合わせや想定業務から、正常系・境界系・意地悪な質問を混ぜた20〜30件の入力と合格条件（バイナリ判定できる基準）をスプレッドシートやJSONにまとめる。
2. **失敗ケースを10件読んで「失敗モード」を3〜5種類に分類する**: いきなりプロンプトを書き換えず、検索漏れ（コンテキスト再現率不足）・根拠なき捏造（忠実度不足）・ツール引数誤り・形式崩れのどれが一番多いかを数えて最大要因から潰す。
3. **PR時のスモークEvalsと「本番失敗の還流」を仕組み化する**: 変更のたびに最低限の **プロンプト回帰テスト** と **構造化出力準拠率** をCIで自動実行し、本番で見つかった失敗事例を毎週評価セットへ追加する **評価データフライホイール** を回し始める。

### 4. 理解度チェック・ミニクイズ

**Q1. 本番の請求照合エージェントで「10回中1回でも当たればいい」のではなく、「毎回安定して成功すること」を評価したい場合、どちらの指標を使うべきですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：Pass^k 指標（Pass^k Consistency Metric）**
Pass@kは「k回試して1回以上成功する確率」を測るため、不安定なモデルでも高く出ます。本番業務の信頼性を見るには、k回連続ですべて成功する一貫性を測る **Pass^k 指標** が適しています。

</details>

**Q2. RAGチャットで「参照文書には書かれていない条件を、AIがもっともらしい文章で勝手に捏造して回答してしまう」問題を防ぐため、RAG評価トライアドの中で最優先で測るべき指標は何ですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：忠実度評価（Faithfulness / Groundedness Eval）（およびハルシネーション率測定）**
回答に含まれるすべての主張が、検索されたコンテキスト文書に裏付けられているかを検証することで、根拠なき捏造（ハルシネーション）を定量検知できます。

</details>

**Q3. 評価スコアが82%で頭打ちになり、プロンプトをいろいろ書き換えても改善しません。次に取るべき最も効果的なアクションはどれですか？**
<details>
<summary>解答と解説を見る</summary>

**答え：エラー分析ワークフロー（Systematic Error Analysis）と失敗モード分類体系の作成**
スコアという数字だけを見て手探りでプロンプトを弄るのではなく、失敗した実例を人間が直接読み込み、根本原因（検索漏れ、ツール誤用、形式崩れ等）を分類して最大ボトルネックから対策するのが最も確実です。

</details>
